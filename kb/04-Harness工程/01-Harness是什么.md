# Harness 是什么：模型之外的那一层

> 结论：**模型决定上限，Harness 决定能不能触达上限。** 两者是两层，不能混为一谈。

## 两层的定义

| 层 | 代表 | 本质 |
|---|---|---|
| **模型层** | Claude Opus 4.8 / GPT-5.5 等 | 真正干活的「大脑」，只负责「根据输入 Prompt 输出 Token」 |
| **Harness 层** | Claude Code、Codex、DSH、Claude Design | 提示词 + 工具链 + 上下文管理 + 权限沙箱 + UI 交互流程 |

比喻：**Harness 是厨房**（锅碗瓢盆＝工具，菜谱＝Skill），**模型是厨师**。同一套厨房换个厨师，菜不一样；同一个厨师换厨房，能做的菜也不一样。

## 关键论断：Harness 无法被模型「内化」

模型每轮训练确实会把「什么时候调工具、怎么拆任务、失败怎么回退、什么代码风格更好」这类**策略与判断**学进权重；但真正去**执行**的，全是 Harness：

- 打开电脑、跑 Blender、操作浏览器；
- 管理上下文窗口、把结果喂回；
- 决定哪些操作要用户确认、防止误删文件；
- 任务中断后怎么恢复（checkpoint）。

**你只能训练「如何操作工具」，训练不了「工具」本身。**

## Harness 里到底装了什么

```
系统提示词与角色设定
工具（Tool）定义与调用循环
上下文窗口管理（截断、压缩、注入、检索）
权限与沙箱
结果回灌（工具输出如何进入下一轮）
失败重试与检查点恢复
子代理 / 后台任务 / 工作流调度
```

前六项决定「能不能可靠干完」，后两项决定「能不能并行、能不能长期跑」。

## 三条推论

1. **换模型 ≠ 换效果**。同 Harness 换模型，差异来自判断力；同模型换 Harness，差异来自能不能把事做完。
2. **Harness 好用的根源常在工程文化**，不在模型。Claude Code 的 Harness 被归因于开源社区与 Unix 哲学（小工具、可组合、可脚本化）。
3. **「模型够强了，Harness 会消失」是误判**。模型越强，Harness 越要负责边界：权限、沙箱、恢复、审计。

## 与上下文工程的关系

三层递进：**提示词**决定这一次的说法 → **上下文工程**决定模型回答那一刻「眼里有什么」→ **Harness** 决定这一切如何被组织、约束、回灌。

三者不是替代关系：写更好的提示词，解决不了「没有工具」；加更多工具，解决不了「上下文爆炸」。

## 怎么判断一个 Harness 好不好

| 维度 | 观察点 |
|---|---|
| 完成率 | 长任务能不能跑到终点，而不是半路失忆 |
| 可恢复 | 中断、崩溃后能不能接着干 |
| 边界 | 危险动作有没有确认、沙箱、最小权限 |
| 可观测 | 出了事能不能看到「哪一轮、哪个工具、什么参数」 |
| 可扩展 | 加一个 Skill / MCP 要不要改代码 |
