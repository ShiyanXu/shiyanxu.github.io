# 多模型分工与编排

> 一条主线：**主模型不做苦力，只做判断**。来源 #42、#44、#45、#46、#5。

## 角色分工范式（#42）

| 角色 | 模型 | 职责 |
|---|---|---|
| 规划 | Fable 5 | 做规划与文档 |
| 建模 | Kimi K3 | 建立虚拟项目、核查代码实现是否与文档一致 |
| 实现 | GPT-5.6 Sol | 具体编码与调试 |
| 执行 | Grok 4.6 Hermes Agent | 落地执行 |
| 人类 | 「我：按回车」 | 拍板与验收 |

这是「按能力切模型」而非「一个模型包打天下」的典型配置。

## 主模型只做编排（#44）

主模型（Fable）只做**分析、编排和验证**，具体任务（读大量代码、写代码、跑测试、批量修改）一律交给 subagent（Opus / Sonnet）。

**要点：主模型用 High 档就够（或 Medium），切忌开到 Max 及以上。** 原因不是省钱，而是 Max 档单轮消耗的上下文更多，更容易提前触发压缩，反而破坏长任务的连贯性（机制见 [思考强度与上下文压缩](../08-模型与推理/02-思考强度与上下文压缩.md)）。

可直接抄的提示词骨架：

```
注意你的主要任务是分析、编排和验证，具体任务尽可能交给
subagent（Opus 或 Sonnet）去执行。自己只做需求澄清、方案拆解、
任务分发和结果验收，实现类工作（读大量代码、写代码、跑测试、
批量修改）一律用 Agent 工具派给 subagent 执行。
```

## meta agent 模式（#45，读者实践）

用一个 meta thread 管大 scope：在 thread 内讨论高维决策 → 让 meta agent 写 spec → sub agent 执行 → 最后 meta agent verify。

适用：跨模块、跨周的工程；不适用：一两小时能收尾的小任务（协调成本大于收益）。

## 编排插件化（#46）

把「大模型指挥小模型」做成插件：Fable-Advisor 让 Fable 5.1 编排 GPT-5.6 Luna，宣传语是 **In-context distillation: Fable-level intelligence at a fraction of the cost**（用上下文蒸馏，以极小成本获得 Fable 级智能），流程固定为 **Orchestrate → Implement → Review**。

「上下文蒸馏」与「把大模型知识蒸进小模型权重」（KD）不同：这里是**在推理时把小模型放进大模型编排的上下文/工作流里**，让它「站在大模型肩膀上」执行。

## 按任务切模型的路由器（#5）

Claude Code Router（CCR）按「上下文 / 思考 / 后台 / 工具」等策略切换不同大模型 API，让长上下文模型（DeepSeek-V4-Pro 1M 窗口）与高性价比模型（GLM-5.1）互补，最终效果「媲美顶级模型」。

- 最大收益：**一次开十几个子 Agent 并发任务**的成本与速度。
- 主要难点：**把提示词里的 tag 标记如实传给被调用的小模型**——路由层最容易丢掉任务标签。

## 成本与质量的三条经验

1. **强模型做判断，弱模型做执行**：判断错了全盘错，执行错了可以重跑。
2. **档位不是越高越好**：主模型 High/Medium，执行 subagent 用中档，把预算花在「多跑几轮」上。
3. **并发换时间**：子代理并行的瓶颈是调度与合并，不是模型速度。
