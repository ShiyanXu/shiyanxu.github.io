# 两头理论：用好 Coding Agent，关键在开头和结尾

> 这是全批内容中被反复强调、也最可操作的一条。原报告里它来自宝玉xp 的一条微博及其配套信息图（#8、#9）。

## 结论

**开头最重要**：一开始的方向和设定错了，后面怎么改都改不好。**先做 Plan，不要一上来就写代码。**

## 六步流程

1. **核心原则**——重要的开头和设定；先把设计想清楚，再让 Agent 动手。争的是「方向 + 速度」，不是「谁先写出代码」。
2. **先做 Plan**——把功能需求简单整理，**同时发给 3 个不同 Agent（Codex、Claude Code、Cursor）**，都开 Plan 模式，尽量用最好的模型。
3. **比较多个 Plan，选最优方案**——比较 A/B/C，取长补短、融合优化；不满意就退回迭代。
4. **按复杂度决定怎么执行**——简单 Plan 直接编码；复杂 Plan 拆成几个 Phase，每个 Phase 写清「要求 + 验证方法」，存成 Markdown。
5. **按 Phase 推进，必要时人工纠偏**——**越早纠偏，成本越低**。
6. **最后 Review，不必太多 Agent**——重点看是否符合设计要求、代码质量有没有问题。

类比：请几位高水平架构师各出一套系统设计方案，你来拍板，再交给程序员执行，最后请高手 review。

## 为什么有效：修复成本随阶段指数上升

软件缺陷的修复成本沿「需求 → 设计 → 编码 → 测试 → 上线」逐级放大。「先 Plan、多方案比较、Phase 化推进」的本质，是把纠错环节**尽量前移到成本最低的设计阶段**。AI 让编码变快之后，这条规律的杠杆反而更大——因为编码不再是瓶颈，设计错误反而更贵。

## 落地要点

- **Plan 模式是解耦工具**：它把「方向决策」与「实现」分开，人工确认前不动代码。
- **三份 Plan 的价值在差异，不在数量**：三份都同质，等于把同一个偏见复制三份；比较时要问「这份方案在哪个约束下更优」。
- **Phase 文档是给 Agent 的合同**：每段写清输入、输出、验收标准，Agent 才能自验证。
- **Review 阶段减 Agent 数量**：评审是判断工作，多 Agent 反而互相稀释。

## 按复杂度分流

| 复杂度 | 做法 |
|---|---|
| 简单（单文件、改样式、脚本） | 一份 Plan，直接编码，人工扫一眼 |
| 中等（多文件、加功能） | 2–3 份 Plan 比较，拆 2–4 个 Phase |
| 复杂（新系统、重构） | 3 份 Plan + 架构图 + 设计文档，Phase 化交接，逐段验收 |

## 可复用清单

```
1. 需求 → 同时给 3 个 Agent 出 Plan（都开 Plan 模式，用最强模型）
2. 比较 3 份 Plan → 取长补短，人工拍板
3. 复杂任务拆 Phase，每 Phase 写清「要求 + 验证方法」，存成 Markdown
4. 按 Phase 交给执行型 Agent，主模型只做编排与验收
5. 长任务用 Ralph Loop：目标写进 MAIN.md，每轮全新上下文对照修正
6. 全程守住：测试覆盖、日志、安全、性能；高风险操作要人工确认
```
