# 提示词的分层与工程化

> 把「给 AI 的输入」拆成三层，才能回答「该改哪一层」。来源 #18、#27、#15。

## 三层结构

1. **提示词**：用户当次把输入当作一种提示词。决定「这一次怎么说」。
2. **上下文工程 / Skill**：把 AI 能获取的信息、以及它应该知道的既有知识告诉它。决定「回答那一刻眼里有什么」。
3. **Harness**：以上全部，作为「给 AI 的输入」的系统层。决定「这些如何被组织、约束、回灌」。

业界共识：**上下文工程比提示词措辞更能决定复杂任务成败。**

## 该怎么判断改哪一层

| 症状 | 该改的层 |
|---|---|
| 这一次输出格式不对 | 提示词（补格式要求） |
| 每次都要重复交代同样的规矩 | Skill（固化） |
| 模型不知道项目背景 | 上下文文件 / 检索（`AGENTS.md`、docs） |
| 模型拿不到最新数据 | MCP / 工具 |
| 模型记得前面说过的话，但前后矛盾 | Harness（压缩策略、状态管理） |
| 模型能说但做不了 | Harness（工具、权限、执行循环） |

## 提示词的四要素

写任何一条提示词，检查是否包含：

1. **角色 / 场景**：你是以什么身份、在什么局面下回答；
2. **目标**：要产出什么、给谁看、用来做什么决定；
3. **约束**：不能碰什么（合规、格式、技术栈）；
4. **验收**：什么样的答案算好（长度、结构、必须包含的字段）。

缺 2 会答非所问，缺 3 会越界，缺 4 会无限展开。

## 把好提示词工程化

一次性提示词的三个问题：**不可复用、不可评测、不可维护**。工程化的路径：

| 阶段 | 做法 |
|---|---|
| 记录 | 把有效的提示词存进笔记，标注场景与效果 |
| 版本化 | 每次修改留「为什么改」，像代码一样有历史 |
| 评测 | 用 5–10 个真实输入跑一遍，看输出是否稳定 |
| 固化 | 稳定后封装成 Skill（见 [写Skill与迭代Skill](../05-Skills体系/03-写Skill与迭代Skill.md)） |
| 组合 | 明确「系统提示词 / 用户提示词 / Skill / MCP」各管一段，不重复 |

这也是为什么社区里「好提示词 → 开源成 `/grill-me` 这类 Skill」成为主流路径。

## 常见误区

1. **堆形容词**（「请非常仔细、极其认真地……」）——模型对程度副词不敏感，对具体约束敏感。
2. **一次给十条规则**——超出注意力预算，规则会互相稀释。宁可拆成两轮。
3. **用提示词补工具缺失**——「请你记住这个文件内容」不如直接给文件读取工具。
4. **在提示词里写长篇背景**——背景应该进 `AGENTS.md` / 检索，而不是每轮复制。
5. **只改措辞不改结构**——输出不稳定往往是「缺验收标准」，不是「措辞不够礼貌」。
