# 交代全局上下文 ＞ 写死局部约束

> 来源 #48。这是全批提示词内容里最反直觉、也最省事的一条。

## 结论

模型能力已很强，**不要写具体的局部约束、不要举极端例子**——模型知道「汽车」是什么，不需要写成「四个轮子的金属长方体」。

模型「不听话」往往不是你指令不够细，而是**没交代全局上下文**。

## 它到底在问什么

写代码前，把这些交代清楚：

- 你写的是**内部项目还是开源项目**？
- 项目属于**什么组织**？
- **是否已发布**？
- **最终使用场景**是什么？
- **由几个人维护**？
- **你是什么角色、负责哪部分**？

交代了这些，模型就不会纠结「单元测试写成什么样、接口设计成什么样」，也不会自作主张给你规划 v1/v2。

## 为什么有效

现代 LLM 的内部表征已包含大量世界知识（world model）。过细的局部约束会：

1. **占用宝贵的上下文预算**；
2. **与模型自身的先验冲突**，诱发「机械执行」而非「理解目标」；
3. 在边界情况下**反而限制**模型的合理发挥。

更有效的做法是提供 **目标 + 约束条件 + 验收标准**，让模型在约束内自行决策。

| 差 | 好 |
|---|---|
| 「写一个函数，先判空，再循环，循环里 if x>0 就……」 | 「把这段逻辑改成幂等的，输入可能为 null，返回 Result 类型，保持现有日志格式」 |
| 「用现代风格写 CSS」 | 「这是内部后台，只支持 Chrome 最新版，可读性优先于兼容性」 |
| 「加单元测试」 | 「这是开源库，测试要能被外部贡献者直接跑，不用 mock 框架」 |

## 与「如何跟 AI 交流」的关系（#29）

向身边最会做汇报的人请教：用**清晰的目的、准确的步骤、明确的结果**去沟通。

顺序是：交代所有背景 → 给足标准 → 执行尽可能一步步拆解 → 仔细核查每一步结果 → 复盘改进。

本质与「全局上下文」一致：**先让对方知道你在什么局里，再谈这一步怎么做。**

## 边界：什么时候仍要写死细节

- 合规/安全红线（必须逐条列出，不可交给模型判断）；
- 与模型先验相反的内部约定（如「本项目禁止使用 ORM」）；
- 精确的格式契约（字段名、状态码、错误码）。

原则：**「为什么」交给上下文，「不能碰什么」写成硬约束。**
