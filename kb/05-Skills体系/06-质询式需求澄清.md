# 质询式需求澄清：grill-me 与 grill-with-docs

> 结论：最贵的返工发生在写代码之前。这两个 Skill 把「需求澄清」做成一场有结构的审问——**grill-me 只产出共识，grill-with-docs 顺手把共识写进术语表和 ADR**，访谈确认完再动手。

## 它们补的是哪一环

直接上手开发，漏掉的通常是这些东西：现有代码里已经存在两套编码、职责边界没说清、边界场景没想过。等代码写完再发现，修的是实现；在对话里发现，改的只是一个约定。

这两个 Skill 都来自 `mattpocock/skills`，区别只在于**共识要不要沉淀成文档**。

| | grill-me | grill-with-docs |
|---|---|---|
| 形态 | 连续、深度的针对性提问，追着决策树往下问 | 同样的质询，但用项目已有的术语表和架构决策来挑战你 |
| 产出 | 只有对话共识 | `CONTEXT.md`（只作术语表，不含实现细节）+ 必要时一条 ADR |
| 适用 | 通用场景、还没有代码库约定 | 已有代码库和术语体系、要把决策留下来 |

它扮演的角色像一个极其严谨的工程师或架构师：不放过细节，一层层追问，直到方案可执行。

## grill-with-docs 的特殊之处

它不凭空提问，而是拿你项目里**已有的东西**来质疑：

- **术语冲突**：你说的词和术语表里的定义不是一个意思；
- **边界场景**：你说「检测到就处理」，那没检测到呢、检测器挂了怎么办；
- **代码与口述不一致**：你描述的行为和现有实现不一样，当场指出来。

ADR 不是想问就写，门槛是三条同时成立：**难以回退、没有上下文会令人困惑、是真实权衡的结果**。不满足就只更新术语表。

## 安装

仓库：`https://github.com/mattpocock/skills`

做法很简单：**直接让 Agent 装**，说「安装 grill-me 和 grill-with-docs」，它会识别技能包并连带装上依赖技能（`grilling`、`domain-modeling`）。分享里的实测是 9 步、1 分 11 秒装完，落盘位置：

```
~/.copilot/skills/grill-me
~/.copilot/skills/grill-with-docs
~/.copilot/skills/grilling          # 依赖
~/.copilot/skills/domain-modeling   # 依赖
~/.agents/skills/                   # 全局代理目录
```

## 怎么用

1. 有了想法或需求，在对话里直接调用技能，把需求说清楚；
2. 它开始就实现细节逐条提问，每条附建议，你确认或纠正；
3. 多轮访谈后得到**最终共识**，这时才让它开始实现。

分享里给的首轮耗时是 5 步、3 分 39 秒——比事后返工便宜得多。

## 一个真实案例

需求：写一个 `dfx_leak_monitor.py`，监控漏液检测状态。

**它先指出问题**：现有代码有两套状态编码（`leak_monitor.py:49` 与 `wb_leak_detector_driver.h:6`），不能直接混用。

**然后逐条追问**：

- Q1 首期是否只针对 B6120-BL，是否预留多产品扩展？→ 是，该产品已有三个 S3IP 漏液检测器配置。
- Q2 新脚本是否只做 DFX 诊断，记录状态变化，不负责下电、D-Bus/Redfish 上报或复用旧监控？→ 是，先把诊断和设备保护职责分开。

**你的补充把约定定死**：参数通过 `DFX_LEAK_MONITOR_PARAM` 字典配置；检测到漏液后持续记录日志并处理；检测器断开后持续记录；据 `leak_detector/strategy` 判断是否下电（0 不下电，1 下电）。

**最终共识 22 项**，分组成表：

| 组 | 结论 |
|---|---|
| 定位 | 独立 DFX 诊断脚本，不改现有 `leak_monitor.py` |
| 产品 | 仅 B6120-BL 注册 |
| 状态源 | S3IP `/sys/s3ip/leak_detector/`，检测器数量自动发现 |
| 判定 | `present=0` / `status=0` 跳过；`2` 漏液；`3` 断绳；其余读取出错 |
| 计时 | 各类独立，任一轮恢复即清零重计，启动首轮也须等满时长 |
| 下电 | 仅 `status=2` + `strategy=1`，全局一次并锁存，断绳绝不下电 |
| 配置 | `interval` / `leak_duration` / `break_duration`，可选 `power_down_cmd`（缺省 `psu_off=1`） |
| 日志 | 脚本日志带走转；syslog 仅故障成立与恢复，`common_syslog_crit("DFX_LEAK_MONITOR", msg)` |
| 异常 | `number` 不可用则退出非 0，交由进程管理重启 |

**产出**：`GLOSSARY.md`、`ADR 0001`；随后 7 项待办逐项验证（移植驱动电压模式、移植 sysfs 节点、接入 device_driver 与 switch_driver、静态校验、提交逐项验证……）。

## 为什么值得用

- **把验证成本前移**。同样是发现问题，在访谈里改一句话，在代码里要改一堆；
- **对 AI 协作尤其要紧**。模型会顺着你的描述往下写，不会主动提醒你「这里有两套编码」「职责还没分」。质询型 Skill 就是那个替你追问的角色；
- **有文档的版本能复用**。术语表和 ADR 留下来，下次同类任务不必重新对齐，也让后面的 Agent 少犯同样的错。
