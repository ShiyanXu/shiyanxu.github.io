# Skill 的边界：与 MCP、Subagent、Prompt 怎么分工

> 这四种东西经常被混为一谈。记住一句话：**MCP 负责「能连上」，Skills 负责「知道怎么干」，Subagents 负责「分头干」，Prompts 负责「这一句交代清楚」。**

## 官方对比表

| 维度 | Skills | Prompts | Projects | Subagents | MCP |
|---|---|---|---|---|---|
| 提供什么 | 流程性知识 | 即时指令 | 背景知识 | 任务委派 | 工具连接 |
| 本质 | 可移植专业知识 | 单次对话指令 | 工作区内上下文 | 独立任务处理器 | 外部工具与数据源 |
| 持久性 | 跨对话、跨项目 | 仅当前对话 | 工作区内 | 任务期间 | 持续连接 |
| 加载时机 | 按需动态加载 | 每一轮 | 项目内常驻 | 被调用时 | 始终可用 |
| 含代码 | 是 | 否 | 否 | 是 | 是 |
| 类比 | 给新员工的培训手册 | 临时口头交代 | 入职资料包 | 外包团队 | 给员工配的工具 |

## 一句话辨析

- **Prompt**：这一次怎么说。「帮我把这个函数改成异步」。
- **Skill**：这一类事怎么做。「把 PR 描述写清楚」的完整套路。
- **MCP**：能碰到什么。「能读数据库、能开浏览器」。
- **Subagent**：谁去做。「这件事派给一个独立代理，跑完把结论带回来」。

## 官方规则：MCP 指令 vs Skill 指令

- **MCP 指令**只应包含「如何正确使用该服务器及其工具」的**通用说明**（如某 CRM 的 MCP 说明查询语法与 API 格式）。
- **Skill 指令**负责「在某个具体流程 / 跨服务器工作流中如何使用它们」（如先查哪些记录、如何与聊天记录交叉比对、输出如何组织）。
- **注意冲突**：若 MCP 要求返回 JSON、而 Skill 要求输出 Markdown 表格，模型会陷入「听谁的」的困惑。规则是：**由 Skill 决定最终产出形态，MCP 只负责取数。**

## 什么时候该做成哪一种

| 你的需求 | 该做成 |
|---|---|
| 「每次都要重复交代同一套流程」 | Skill |
| 「模型碰不到我们的内部系统」 | MCP Server |
| 「任务太大，主上下文被中间过程淹没」 | Subagent |
| 「只是这一次想让它按某个格式输出」 | Prompt |
| 「团队共用一套项目背景」 | `AGENTS.md` / Project 配置 |

## 常见误用

1. **把工具文档塞进 Skill**：应该写在 MCP 的 `description` 里，否则 Skill 变成过期文档。
2. **用 Skill 替代 Subagent**：Skill 不能让模型「分身」，只能让它「知道」。
3. **用 Prompt 替代 Skill**：一次性交代无法积累，也无法被评测。
4. **一个 Skill 里调三个 MCP**：可以，但要在正文里写清「先调谁、失败了怎么办」，否则模型会并行乱调。
