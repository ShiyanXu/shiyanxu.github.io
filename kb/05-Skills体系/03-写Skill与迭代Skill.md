# 写 Skill、评测 Skill、迭代 Skill

> 三件事：**别用超高档写**、**像软件一样迭代**、**有一套可复用的生产流水线**。来源 #21、#17、#32、#57。

## 一、写 Skill 的取舍：不要「一步到位」

不建议直接用最强模型「用超高档」来写 Skill。问题不是浪费 token，而是**做得太全反而抓不住重点**——像刚进公司、能力很强、但把轻重缓急全塞进一份文档里的新人，反而让人晕。

可行做法：**先用轻量模型写初版，再让强模型改**，审核会更稳。

理由：
- 轻模型倾向于产出「最小可用结构」，不会过度设计；
- 强模型擅长发现「哪里不精确、哪里会误触发」；
- 两轮下来，Skill 的**边界**比**内容**更清楚。

## 二、Skill 必须像软件一样迭代

用户越多、场景越杂，遇到的边角问题越多。典型 bug：导出海报样式错位、渐变消失。

迭代闭环：

```
自己用 → 发现问题 → 让 Agent 分析原因 → 让 Agent 出解决方案
      → 确认方案 → 更新 Skill → 自己再用
```

要点：
- **问题必须来自真实使用**，不要凭想象补功能；
- 分析原因和出方案分两步做，避免 Agent 直接改出一个「看起来能跑」的补丁；
- 每次更新留一句「为什么改」，否则半年后没人敢动。

## 三、评测：Skill 也需要测试

| 评测项 | 怎么做 |
|---|---|
| **触发评测** | 给 10–20 条真实用户说法，看哪些该触发没触发、哪些不该触发却触发 |
| 格式校验 | frontmatter 字段齐全、`name` 不与已有冲突 |
| 上下文预算 | 正文行数 / token 数是否超预算（超了就该拆 `references/`） |
| 输出质量 | 同一输入跑 3 次，看是否稳定；不稳定说明指令有歧义 |
| 安全 | 扫描密钥、API key、内部链接是否泄露 |

## 四、一条完整的生产流水线（qiaomu-meta-skill，用 Skill 创建 Skill）

把提示词、SOP、聊天记录、旧 Skill、脚本或一个模糊想法交给 Agent，它会自动完成：

```
需求收敛 → 同类检索 → 取长避短 → Skill 设计 → 触发评测
→ 格式校验 → README → API 泄露检查 → PR → Release → npx 安装验证
```

相比普通「生成 SKILL.md」强在哪：
- 先搜索现有 Skill 库（skills.sh / SkillsMP），避免重复造轮子；
- 回 GitHub 核对来源、维护状态、安全与许可证；
- 记录 **keep / adapt / reject / invent** 四类决策，避免拼贴抄袭；
- 区分「设计优势」与「待验证假设」；
- 校验版本、上下文预算与递归发现；
- 自动生成 README 与 License；
- 扫描 Secret / API 泄露；
- 走功能分支 → PR → 检查 → Release。

**这条流水线的价值不在自动化，而在「把 Skill 当发布物对待」。**

## 五、什么任务值得写成 Skill

| 类型 | 例子 | 适合？ |
|---|---|---|
| 文档类 | 按固定风格改写文章、生成课程笔记、整理会议纪要 | ✅ 流程稳定 |
| 代码类 | 按团队标准做 PR Review、修 CI、迁移测试写法 | ✅ 有判断标准 |
| 交付类 | 生成 PPT、导出 PDF、打包提交材料 | ✅ 输入输出明确 |
| 集成类 | 按固定流程查 GitHub、飞书、Gmail、Slack | ✅ 步骤可复用 |
| 一次性聊天偏好 | 「以后回答短一点」 | ❌ 用普通提示词 |
| 全项目通用规则 | 「本项目用 pnpm、禁止新增依赖」 | ❌ 放 `AGENTS.md` |

判据：**重复出现 + 步骤稳定 + 需要专业判断**。三条缺一，性价比就低。

## 六、写法规范

- **命名**：小写 kebab-case，如 `doc-review`、`github-fix-ci`；`description` 写清触发场景。
- **正文不写百科**：优先写执行步骤、输入输出、边界、验证方式、异常处理。例如「输入是 Markdown 文档，输出是问题列表；遇到无权限文件跳过并告知；需要人工判断时暂停询问」。
- **分层放材料**：长参考资料进 `references/`，脚本进 `scripts/`，模板进 `assets/`。
- **讲清风险**：脚本若联网、写文件或调外部系统，要写明风险与审批边界。
- **不写密钥**：凭据一律走环境变量。

用 Codex 的 `skill-creator` 时，它通常提醒三条：

1. **concise is key**：说明简短，别写成百科全书；
2. **适度自由度**：给判断空间，但别放任偏离目标；
3. **保护验证完整性**：验证方式要能真正判断题「Skill 是否按预期工作」。

标准结构：`SKILL.md` 必需，`agents/openai.yaml` 推荐，`scripts/` / `references/` / `assets/` 可选。流程是「从具体例子出发 → 规划资源 → 初始化目录 → 编辑 → 校验 → 迭代 → forward-test」。

## 七、用官方文章反向优化自己的 Skill

OpenAI《Rethinking skills and prompts for GPT-6 Astra》里的「Better skills」章节，可**直接复制给模型**，让它审查并优化你自己的 Skill。这比自己反复读更有效——模型对「指令是否可执行」很敏感。

## 八、一页检查表

```
写之前：这件事会重复发生吗？有好坏标准吗？模型默认做不好吗？
写之中：description 写触发场景；正文 ≤100 行；大材料进 references/
写之后：触发评测 → 输出稳定性 → 安全扫描 → 版本号
用起来：每次出问题都回到「哪条指令没写清」
```
