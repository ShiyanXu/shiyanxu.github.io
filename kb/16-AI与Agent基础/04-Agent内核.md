# M4 Agent 内核

> 一句话：一个 agent = **一个循环 + 一堆机制**。循环从第一讲到最后一讲一行没改，其余 14 条都是在它周围挂东西：给工具、划权限、加钩子、压上下文、记事情、分任务、开多线程、拉队友。把这 15 条逐条过完，自建 agent 就没有黑箱了。

**统一记号**：下文 `messages` 指发给模型的消息数组，`tool_use` 指模型请求调用工具，`tool_result` 指程序回填的执行结果。

---

## M4-01 Agent 是什么

**一句话**：Agent 是「为了一个目标，自己决定下一步并采取行动」的系统——判据不是它用了模型，而是**下一步做什么由它自己决定**。

### 是什么

三个层次的对照，划清边界：

| 形态 | 谁决定下一步 | 例子 |
|---|---|---|
| 单次问答 | 人（一问一答） | 翻译一段文字 |
| 工作流 | 事先写死的代码 | 固定的 ETL 流程 |
| Agent | 模型，运行时决定 | 「把这个 bug 修了，跑通测试」 |

它不是「更聪明的聊天」，本质差别有三条：**有循环**（能连续行动）、**有工具**（能产生真实副作用）、**有终止判定**（知道何时停、何时求人）。

### 怎么运作

```
目标 → 观察当前状态 → 决定下一步（模型）→ 执行（工具）→ 更新状态
     → 判断：完成？失败？该问人？ → 继续或退出
```

这条「观察-决策-执行-判定」的闭环，就是后面 14 条机制要服务的对象。

### 什么时候用它

- 任务步骤不确定、需要边做边看 → agent。
- 步骤固定、每次都一样 → 写成代码，又快又省（agent 在这类任务上是纯浪费）。
- 需要明确责任边界、可审计 → 必须是工作流 + 人工批准点。

判据：**同一任务跑三次，步骤会不一样吗？** 会 → agent；不会 → 别用 agent。

### 易错点

1. **把「会调一个工具」叫 agent**，其实那是 function calling。
2. **给 agent 一个模糊目标**，它会用几十轮探索替你确认需求，成本远超直接问。
3. **不给终止条件**，它能一直「再优化一下」，直到烧完预算。

## M4-02 Agent Loop

**一句话**：整个 agent 的内核只有一个 `while True`——问模型、执行它要的工具、把结果塞回去、再问，直到它不再要工具为止。

### 是什么

最短可运行的 agent 只有 20 行：

```python
def agent_loop(messages):
    while True:
        resp = client.messages.create(model=M, system=S, messages=messages, tools=TOOLS)
        messages.append({"role": "assistant", "content": resp.content})

        tool_calls = [b for b in resp.content if b.type == "tool_use"]
        if not tool_calls:          # 不再要工具 = 它认为说完了
            return

        results = []
        for call in tool_calls:
            output = TOOL_HANDLERS[call.name](**call.input)
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": output})
        messages.append({"role": "user", "content": results})
```

四行是关键：**追加 assistant 消息**（保住它自己的意图）、**检出不调工具**（唯一正常出口）、**执行并回填**（`tool_use_id` 必须对上）、**循环**。

### 怎么运作

一次迭代就是一问一答一执行。所有后续机制都插在这四步的空隙里：

```
[压缩上下文] → 调模型 → [权限检查] → [hook 前后] → 执行工具 → [记录/通知] → 回到开头
```

理解这一点，M4-03 到 M4-15 就不再是 14 个孤立功能，而是 14 个「插在哪一步」的选择。

### 什么时候用它

永远在用它。判断自己是否真的理解 agent，就看能不能在不看文档的情况下把这 20 行写出来——写不出来，后面所有机制都只是抄配置。

### 易错点

1. **漏掉 assistant 消息回填**，模型下一轮看不到自己刚才的决定，行为立刻混乱。
2. **用文本匹配判断「是否要调工具」**（比如找 "```tool"），应该用结构化字段。
3. **无最大轮次限制**，出错时无限循环，一晚上烧掉一个月预算。

## M4-03 Tool Use

**一句话**：加一个工具 = 加一个 handler，循环一行不改——工具与循环解耦，是 agent 能持续长大而不会烂掉的前提。

### 是什么

工具在系统里是三层结构：

| 层 | 内容 | 谁看 |
|---|---|---|
| 声明 | 名字、描述、参数 schema | 模型看（决定调不调） |
| 分发 | `name → handler` 的映射表 | 运行时用 |
| 实现 | 真正干活的函数 | 你的代码 |

再加两条工程约束：**参数校验**（schema 只是建议，实现里必须再校验一次）、**超时与错误包装**（工具失败不能炸掉循环，要变成一条「失败」的 tool_result 返回给模型）。

### 怎么运作

```python
TOOL_HANDLERS = {"read_file": read_file, "run_bash": run_bash}

def dispatch(call):
    h = TOOL_HANDLERS.get(call.name)
    if h is None:
        return f"未知工具：{call.name}"      # 错误也回填，让模型自己纠
    try:
        return h(**call.input)
    except Exception as e:
        return f"工具执行失败：{e}"
```

并发：一轮里模型可能同时请求多个工具，无依赖时并行执行；有依赖时必须串行（比如先读文件再改文件）。

### 什么时候用它

- 工具数量控制在 **10 个以内**，超过就分组或做路由。
- 工具粒度按「一次有意义的动作」切，不要做「万能 bash」——虽然它最灵活，但也最危险、最难审计。

### 易错点

1. **异常直接抛到外层**，整个循环崩掉，会话丢失。
2. **工具名重复或描述重叠**（两个都叫「查资料」），模型只能瞎猜。
3. **把未知工具当致命错误**，其实回填一句提示，模型往往自己就改对了。

## M4-04 权限系统

**一句话**：先划边界再给自由——把「什么可以直接跑、什么必须问、什么绝对不行」写成规则，规则之外一律拦截。

### 是什么

三层判定，从宽到严：

| 层 | 规则形态 | 例 |
|---|---|---|
| 白名单 | 命令前缀 / 路径前缀 | 允许读 `./workspace/**` |
| 审批 | 命中规则就暂停，等人确认 | `git push`、`rm -rf`、发邮件 |
| 硬禁止 | 无条件拒绝 | 写系统目录、读取密钥文件 |

再加一层**沙箱**：即使规则漏了，文件系统与网络的隔离仍是最后一道墙。

### 怎么运作

```
工具调用请求
 → 解析出「动作 + 目标」（命令、路径、URL）
 → 过规则表：allow / ask / deny
 → allow：执行
 → ask：挂起，把「要做什么、为什么」呈现给人 → 等待批准/拒绝
 → deny：回填拒绝理由（模型会换路）
```

关键设计：**拒绝要说明理由**，否则模型会反复用同样方式重试。

### 什么时候用它

- 一切会产生真实副作用的工具（写文件、删文件、发请求、花钱）。
- 无人值守的长任务：必须把「需要人」的动作变成审批队列，而不是让流程卡死。
- 团队共用环境：权限同时是安全边界和责任边界。

### 易错点

1. **只按命令名判断**（允许 `git`），于是 `git push --force` 也被放过。
2. **审批弹窗不给上下文**，人只能盲批，等于没有审核。
3. **默认全允许再逐步收紧**，历史上这样做几乎总会漏。

## M4-05 Hook 机制

**一句话**：Hook 是在循环的固定位置留的扩展点——你能在不碰主循环一行代码的前提下，插入日志、校验、注入、拦截。

### 是什么

常见四类挂点：

| Hook | 触发时机 | 典型用途 |
|---|---|---|
| PreToolUse | 工具执行前 | 权限校验、参数改写、审计日志 |
| PostToolUse | 工具执行后 | 结果脱敏、格式统一、写日志 |
| UserPromptSubmit | 用户输入提交时 | 上下文注入、敏感词拦截 |
| Stop | 一轮结束时 | 触发通知、统计用量、落盘 |

Hook 与「改代码」的区别：Hook 是**配置**（可增删、可版本化），改代码是**分叉**（每个定制都得维护一份）。

### 怎么运作

```python
def run_tool(call):
    for h in HOOKS["PreToolUse"]:
        verdict = h(call)                  # 可返回 allow / deny / 修改后的 call
        if verdict == "deny":
            return "被策略拦截"
    result = dispatch(call)
    for h in HOOKS["PostToolUse"]:
        result = h(call, result) or result
    return result
```

注意：Hook 出异常应当**降级而不中断**（记日志、继续），否则一个坏 Hook 能让整个 agent 停摆。

### 什么时候用它

- 需要审计（谁在什么时候调了什么）→ PostToolUse。
- 需要统一脱敏（手机号、密钥）→ PostToolUse 改写结果。
- 需要「每次启动都自动读项目约定」→ UserPromptSubmit 注入。

不需要动态扩展时，别上 Hook——直接写在循环里更直观。

### 易错点

1. **用 Hook 实现核心逻辑**。Hook 应可随时移除且不影响主功能。
2. **Hook 里再调模型**。延迟与成本翻倍，还可能递归。
3. **静默失败**。Hook 报错被吞掉，你以为是策略生效，其实是没生效。

## M4-06 先规划再执行

**一句话**：把「打算做什么」外化成一份可见的清单，是提升完成率最便宜的手段——它同时约束模型、暴露进度、留下断点。

### 是什么

一份 todo 的最小结构：

```
[ ] 读现有实现，确认入口
[x] 改解析函数，处理空值
[ ] 补一条测试
[ ] 跑全量测试
```

三个作用，缺一不可：
- **约束**：清单写出来了，模型不容易中途跑偏。
- **可见**：人一眼知道进行到哪，不用读日志。
- **可恢复**：中断后从第一条未完成项继续。

### 怎么运作

```
开工前：把目标拆成 3–7 条可验证的步骤，写进清单
执行中：每完成一条立即标记（不要攒着）
遇到计划外发现：先加一条新项，再决定插在哪
收尾：清单必须全绿，否则不算完成
```

关键约束：**每一条都要可验证**（「能跑通」而不是「优化一下」），否则清单会变成自我安慰。

### 什么时候用它

- 任务超过 3 步、或会跨会话 → 必须写。
- 一步就能做完 → 不写，写清单本身也是成本。
- 多人/多 agent 协作 → 清单即任务板（升级为 [M4-11](#m4-11-task-系统)）。

### 易错点

1. **清单写成愿望列表**（「提升性能」），无法判定完成。
2. **做完不标记**，最后自己也搞不清哪些真做完了。
3. **清单与代码不同步**，删了功能却没删条目，下一轮又被捡起来做。

## M4-07 Subagent

**一句话**：Subagent 是「把子任务扔进一个干净的上下文里做完，只把它最后那句话带回来」——它的价值不是并行，是**上下文的隔离与过滤**。

### 是什么

主 agent 与 subagent 的差别只有两条：

| 项 | 主 agent | subagent |
|---|---|---|
| messages | 累积全部历史 | 全新空数组 |
| 返回 | 完整轨迹 | 一句最终结论 |

于是 subagent 读了一百个文件，主 agent 只收到「入口在 src/main.py，配置在 config.yaml」——**中间过程不进主上下文**，这是它最大的作用。

### 怎么运作

```
主 agent 决定委派 → 工具调用 spawn_subagent(task="...")
  → 新上下文：system + 这个任务描述（不带主历史）
  → 子 agent 在自己的循环里跑，可能又调很多工具
  → 结束时只把最终文本作为一条 tool_result 返回
主 agent 继续（上下文只多了一行）
```

### 什么时候用它

- 探索型子任务（「找出所有用到这个函数的文件」）——过程很长、结论很短。
- 需要独立视角（code review、事实核查）——不受主上下文先入为主的影响。
- 并行独立子任务 —— 注意：并行是副作用，隔离才是目的。

判据：**子任务的过程会比结论长得多吗？** 是 → 值得委派；否 → 直接做，多一层只会丢信息。

### 易错点

1. **让 subagent 继承全部历史**，隔离的意义就没了。
2. **返回一大段原文**，等于把隔离又抵消掉。
3. **期待 subagent 记住主线的隐性约定**，它看不到，必须写进任务描述。

## M4-08 Skill 按需加载

**一句话**：Skill 是「先给目录、要用了再展开正文」的知识包——不占常驻上下文，只在触发时把完整流程注入。

### 是什么

三层结构，对应三次加载：

| 层 | 内容 | 何时进入上下文 |
|---|---|---|
| 目录 | 一行名字 + 一句话用途 | 常驻（几十 token） |
| 说明 | 完整步骤、约定、边界 | 任务匹配时 |
| 资源 | 脚本、模板、参考文件 | 真正需要时再读 |

对比之下：把流程写进 AGENTS.md 是常驻成本；写成 Skill 是按需成本。十个流程常驻 5000 token，写成 Skill 常驻 200 token。

### 怎么运作

```
用户请求 → 模型扫目录（每个 skill 一行）
 → 判断「这个请求属于 X」→ 加载 X 的说明
 → 按说明执行（需要时才读它引用的资源）
 → 任务结束，说明从后续上下文中淡出（或下次被压缩掉）
```

### 什么时候用它

- 同一套流程要反复用（周报、发布、代码审查）→ Skill。
- 只用一次 → 直接写提示词，别建 Skill。
- 需要强制每次遵守的硬约束 → 放 AGENTS.md / 系统提示，不要放 Skill（它可能不被触发）。

判据：**「每次都要」还是「有时要」？** 每次都要 → 常驻；有时要 → Skill。

### 易错点

1. **目录描述写得含糊**，模型永远不知道该加载哪个。
2. **Skill 里塞了太多背景知识**，加载成本接近常驻，失去意义。
3. **以为 Skill 一定能触发**，描述与用户表述差太远时就是不会触发。

## M4-09 Context Compact

**一句话**：上下文一定会满，所以必须有「腾地方」的机制——顺序是先削工具输出、再删冗余轮次、最后才摘要历史，反过来做会丢掉最重要的细节。

### 是什么

四级压缩，代价递增、信息损失递增：

| 级 | 动作 | 丢什么 | 保留什么 |
|---|---|---|---|
| 1 | 截断超长 tool_result | 冗长的日志/文件内容 | 头尾与关键行 |
| 2 | 删掉已完成的中间轮次 | 过程 | 结论 |
| 3 | 合并相邻同类消息 | 边界 | 语义 |
| 4 | 摘要整段历史 | 细节 | 决策与约束 |

判据：**压缩后还能回答「我们现在做到哪、为什么这么做」吗？** 不能，就是压过头了。

### 怎么运作

```
每轮开始前检查 token 用量
 → 超过阈值（如窗口的 70%）触发压缩
 → 按 1→4 逐级尝试，直到降到水位以下
 → 摘要时显式保留：目标、已定决策、未完成项、用户硬约束
```

关键设计：**压缩要可追溯**。摘要里丢掉的东西，原始内容应落盘（文件或日志），需要时能读回来——这是 agent 能跑长任务的根本。

### 什么时候用它

- 长任务（几十轮以上）→ 必须自动压缩。
- 短会话 → 不需要，裁剪几轮就够。
- 需要精确回忆早期细节 → 压缩救不了，得靠 [M4-10 Memory](#m4-10-memory) 主动记。

### 易错点

1. **先摘要后删冗余**，把能无损去掉的东西先摘要了一遍，白丢信息。
2. **摘要不保留约束**，压缩后开始违反用户最初的硬要求。
3. **压缩后不重放关键状态**，模型以为任务刚开始。

## M4-10 Memory

**一句话**：记忆不是「把聊天记录存起来」，而是三个动作——选择该记什么、抽取成条目、定期合并去重。

### 是什么

三个子系统，各有独立判据：

| 子系统 | 回答 | 失败表现 |
|---|---|---|
| 选择 | 这句话值得记吗 | 记了一堆废话，检索全是噪声 |
| 抽取 | 记成什么形式 | 存原文，下次读不懂 |
| 固化 | 旧的怎么更新 | 同一事实存了五份，互相矛盾 |

存储分层：**工作记忆**（当前上下文）→ **会话记忆**（当前任务的事实）→ **长期记忆**（跨任务的偏好与结论）。

### 怎么运作

```
一轮结束
 → 选择：是否出现「稳定事实/偏好/决策」？（不是每轮都有）
 → 抽取：写成一句自足的话（谁、什么、为什么），带时间与来源
 → 固化：与已有条目比对 → 新增 / 更新 / 冲突标记
检索时：按当前任务关键词取回少量条目，注入上下文
```

### 什么时候用它

- 跨会话的稳定偏好（「这个项目用 pnpm」）→ 长期记忆。
- 一次性任务细节 → 不要记，靠上下文就够。
- 频繁变化的事实 → 记「当前值 + 时间」，否则会拿着过期信息干活。

### 易错点

1. **全量存对话**，等于没有记忆，只是把上下文问题挪到了数据库。
2. **只增不合并**，三个月后同一件事有八个版本。
3. **不记来源与时间**，无法判断哪条还有效。

## M4-11 Task 系统

**一句话**：把 todo 从「给人看的清单」升级成「给系统看的数据结构」——每条任务有状态、有依赖、落盘持久化，才谈得上恢复与分工。

### 是什么

一条任务记录至少五个字段：

```
{ id, title, status(pending/in_progress/done/blocked),
  blockedBy: [id...], owner?, workdir? }
```

与 todo 的三点差别：**有依赖关系**（DAG，不是线性表）、**有归属**（谁能领）、**有持久化**（进程重启还在）。

### 怎么运作

```
建图：把目标拆成节点，标出依赖（A 完成才能做 B）
调度：找 blockedBy 为空的节点 → 分配 → 标记 in_progress
完成：置 done → 解除下游的 blockedBy → 触发下一批
阻塞：置 blocked + 原因 → 等人或等外部条件
```

依赖关系是这套东西的核心价值：它让「现在能做什么」变成一个可以计算的问题。

### 什么时候用它

- 任务之间有真实依赖 → 需要图。
- 任务独立、只是多 → 清单就够。
- 要给人看进度 → 图比清单更能说明「为什么卡住」。

### 易错点

1. **依赖方向写反**，导致永远没有可执行节点。
2. **状态与代码不同步**，任务标了 done 但代码没提交。
3. **粒度过细**，几百个节点，维护成本超过收益。

## M4-12 后台任务

**一句话**：把慢操作（装依赖、跑全量测试、下载）扔到后台线程，agent 继续思考；完成时用一条通知把结果送回循环。

### 是什么

同步 vs 异步的差别只有一句：**等不等**。

| 模式 | 行为 | 适合 |
|---|---|---|
| 同步 | 阻塞到返回 | 快操作（读文件、查表） |
| 后台 | 立即返回「已启动 + 任务 id」，完成时通知 | 慢操作（分钟级） |

### 怎么运作

```
工具调用 run_in_background(cmd) → 起线程 → 立即返回 task_id
主循环继续做别的事
线程结束 → 把 (task_id, 输出) 推进通知队列
下一轮开头：把队列里的通知作为一条消息注入 → 模型看到结果
```

要点：**通知要注入到消息流里**，而不是让模型主动轮询——轮询会浪费大量轮次。

### 什么时候用它

- 预计超过 30 秒的操作 → 后台。
- 需要并行做多件互不依赖的事 → 后台。
- 有严格顺序依赖 → 老老实实同步。

### 易错点

1. **后台任务失败没有通知**，agent 永远在等一个不会来的结果。
2. **不设超时**，僵尸任务挂着占资源。
3. **多个后台任务输出交错**，不标 task_id 就分不清谁是谁。

## M4-13 定时调度

**一句话**：让任务按时间自己触发，人不再扮演闹钟——这是 agent 从「你叫它才动」变成「它自己会动」的那一步。

### 是什么

三个必须解决的现实问题：

| 问题 | 做法 |
|---|---|
| 进程会重启 | 计划表落盘，启动时重新装载 |
| 机器会睡 | 用系统级调度（cron / 计划任务）拉起，而不是靠常驻进程 |
| 会重复触发 | 记录上次执行时间，幂等设计 |

### 怎么运作

```
注册：{ id, cron 表达式, 任务内容, 上次执行时间 }
触发：调度器到点 → 建一个新的会话/上下文 → 执行任务 → 记录结果
隔离：每次触发用全新上下文（不要继承上一次的），否则会累积漂移
```

### 什么时候用它

- 固定节奏的重复工作（每天早上汇总、每周清理）→ 定时。
- 需要「事件驱动」（文件变了、邮件到了）→ 不是定时，用触发式。
- 只是这一次要做 → 直接做，别建计划。

判据：**这件事需要「没人提醒也会发生」吗？** 需要 → 定时；不需要 → 手动。

### 易错点

1. **依赖常驻进程**，机器一重启就全失效。
2. **任务里带上了「上一次的上下文」**，越跑越偏。
3. **没有失败通知**，静默失败几周都没人发现。

## M4-14 Agent Teams

**一句话**：单 agent 撑不住时，让多个常驻 agent 分活——前提是先有任务图（能领）、有工作目录隔离（不打架）、有协议（怎么说话）。

### 是什么

四个必要条件，缺一个就退化成混乱：

| 条件 | 作用 |
|---|---|
| 常驻队友 | 各自有独立上下文，不共享 messages |
| 原子领取 | 从任务图里「抢」一个 ready 任务，不会两人做同一件 |
| 任务绑定工作目录 | 各自在独立 worktree 里改，避免互相覆盖 |
| 类型化协议 | 消息有类型（请求/结果/阻塞），不是自由聊天 |

### 怎么运作

```
主 agent 拆任务图 → 多个队友并行领取 ready 节点
每个队友：独立上下文 + 独立工作目录 → 干活 → 更新任务状态 → 汇报
主 agent：只接收「结论 + 产物位置」，不接收中间过程
冲突处理：合并前检查任务边界，越界改动打回
```

### 什么时候用它

- 任务能真正切成互不依赖的块 → 值得并行。
- 任务高度耦合（同一文件反复改）→ 并行只会制造冲突，串行更快。
- 需要不同角色（一个写、一个审）→ 团队结构有价值。

判据：**切开后，两块之间需要来回沟通几次？** 超过两三次就别切了。

### 易错点

1. **共享同一个工作目录**，最后靠人肉解冲突。
2. **队友之间自由聊天**，消息量爆炸且无法追踪。
3. **主 agent 事无巨细地指挥**，等于把串行伪装成并行。

## M4-15 MCP 接入

**一句话**：MCP 是工具的「统一插头」——外部能力按同一套协议暴露出来，agent 侧只需要一个客户端，就能把所有工具并进同一个工具池。

### 是什么

三方角色：

| 角色 | 职责 |
|---|---|
| Server | 把某个系统（数据库、浏览器、文件系统）的能力按协议暴露 |
| Client | agent 侧的连接器，负责发现与调用 |
| Host | 运行 agent 的程序，管理多个连接 |

解决的是 N×M 问题：没有协议时，M 个 agent × N 个工具要写 M×N 个适配器；有协议后只需 M + N。

### 怎么运作

```
1. Host 启动时连上若干 server（stdio 或 HTTP）
2. 握手 → 拉取工具清单（名字、描述、schema）
3. 把所有工具并入统一工具池，命名空间防重名（如 fs__read、db__query）
4. 模型调用 → 按命名空间路由到对应 server → 结果原样回填
```

### 什么时候用它

- 需要接入已有系统，且希望多个 agent 共用 → MCP。
- 只是一次性脚本 → 直接写 handler，别为它写 server。
- 需要严格控制权限 → MCP server 是天然的权限边界（它只暴露你允许的那部分）。

### 易错点

1. **工具池被 MCP 塞满**，几十个工具挤在一起，模型选择准确率骤降。
2. **信任第三方 server**，它能看到你传过去的一切。
3. **忽略工具描述质量**，协议统一了格式，不等于描述清晰。
