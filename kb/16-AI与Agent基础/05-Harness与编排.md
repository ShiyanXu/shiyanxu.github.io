# M5 Harness 与编排

> 一句话：M4 是一个个零件，M5 是把零件装成一台机器——**多机制围着同一个循环**（集成 Harness）、**编排形状固定了就写进代码**（Workflow）、**什么时候停由独立判定决定**（Goal Loop）。这一段的分水岭是从「我会用」到「我能设计」。

---

## M5-01 集成 Harness

**一句话**：Harness 不是某个功能，而是**让循环稳定跑下去的整套外围**——工具、权限、上下文、记忆、任务、调度、协议，共用一个循环、一份状态。

### 是什么

「零件齐全」与「装成机器」的差别，就三件事：

| 维度 | 零件堆 | 集成 Harness |
|---|---|---|
| 状态 | 各机制各存一份 | 一份运行时上下文，全员读写同一处 |
| 错误 | 一处报错一处崩 | 统一降级与重试策略 |
| 可观测 | 各打各的日志 | 一条 trace 串起全部动作 |

`Agent = Model + Harness`。模型决定「想做什么」，Harness 决定「能做什么、做过什么、还剩什么、什么时候停」。

### 怎么运作

```
一次迭代里，各机制的调用顺序（这就是「集成」的含义）：

1. 载入运行时上下文：任务、工作目录、权限规则、可用工具、记忆条目
2. 压缩检查（预算超了就压）
3. 调模型
4. 若返回工具调用：权限判定 → PreHook → 执行 → PostHook → 结果回填
5. 若有后台/定时任务完成：注入通知
6. 更新任务状态与记忆
7. 判定是否继续（轮次上限、目标达成、需要人）
```

顺序不是随意的：**压缩必须在调模型之前**（否则这一轮就超了）、**权限判定必须在执行之前**（否则已经造成后果了）。

### 什么时候用它

- 只做一次性任务 → 单机制就够，别提前搭 Harness。
- 要长期跑、要无人值守、要多人共用 → 必须有统一 Harness。
- 要换模型 → Harness 的价值立刻显现：模型可替换，机制不用重写。

### 易错点

1. **每个机制各自持有状态**，最后出现「任务说完成了、上下文说没做」。
2. **没有统一错误策略**，一个工具超时就让整个流程停摆。
3. **把 Harness 当框架**。它是你自己的设计，不是装个包就有的。

## M5-02 Workflow Runtime

**一句话**：当编排的形状已经固定（每次都走同样的分支），就把它从「模型的自由发挥」改成「代码里的一张图」——省 token、可复现、能从中断处恢复。

### 是什么

两种执行模型的根本差别：

| | Agent 自由编排 | Workflow 代码编排 |
|---|---|---|
| 谁决定下一步 | 模型 | 代码（图/状态机） |
| 可复现 | 差（同输入可能不同路径） | 强 |
| 成本 | 每步都要一次模型调用 | 只有节点内调模型 |
| 适用 | 路径不确定 | 路径固定 |

混合形态最常见：**外层是固定工作流，节点内部是 agent 循环**。

### 怎么运作

三个必要构件：

```
1. 图定义：节点（一步动作）+ 边（条件转移）
2. 生命周期事件：节点开始/结束/失败 → 触发回调（日志、通知、指标）
3. journal（日志式持久化）：每完成一个节点就落盘一条记录
   → 崩溃后重放 journal，跳过已完成节点，从断点继续
```

journal 是「可恢复」的全部秘密：**幂等 + 记录已完成**。

### 什么时候用它

- 步骤稳定、要跑很多次（发布流程、每周报告）→ 工作流。
- 步骤不确定、需要临场判断 → agent。
- 长流程且中间可能失败（多步外部调用）→ 必须带 journal，否则每次从头再来。

判据：**同一任务重跑十次，路径会不会变？** 不会 → 写死；会 → 交给模型。

### 易错点

1. **节点不幂等**，重放 journal 时把已经发过的邮件又发一遍。
2. **不记 journal 只记日志**，日志是给人看的，journal 是给恢复用的。
3. **把工作流写成巨型脚本**，分支一多就无法维护，该用图结构表达。

## M5-03 Goal Loop

**一句话**：让「停不停」由一个独立的判定方决定，而不是由干活的那个自己说「我做完了」——这是无人值守能成立的前提。

### 是什么

三种终止方式，可靠性递增：

| 方式 | 谁判定 | 风险 |
|---|---|---|
| 模型自称完成 | 执行者 | 最常见也最不可靠，「做完了」经常是幻觉 |
| 轮次/预算上限 | 计数器 | 能兜底，但不知道是否真完成 |
| 独立评估者 | 另一个判定（可含模型+检查） | 成本高，但能给出理由 |

Goal Loop 的做法：**执行者提出「我要停了」，评估者审查这个提议**，三种结论——通过（真完成）、继续（没完成，附原因）、交还（不可能/失败/超限，请人来）。

### 怎么运作

```
循环：
  执行者工作 → 提出停止
  评估者检查：
    - 目标是否达成（对照可验证的判据，不是「看起来像」）
    - 是否有未处理的失败
    - 是否已超预算/轮次
  → 通过：退出，交付
  → 继续：把「差在哪」作为新指令注入，回到循环
  → 交还：明确说明卡在哪，请人决策
```

评估者的判据必须**事先写成可验证的条件**（测试通过、文件存在、字段齐全），否则它只会复述执行者的说法。

### 什么时候用它

- 需要无人值守跑完（夜间任务、批量处理）→ 必须有。
- 任务短、人就在旁边 → 不需要，人自己就是评估者。
- 目标本身模糊 → 先澄清目标，Goal Loop 救不了模糊目标。

### 易错点

1. **评估者用同一个模型同一段上下文**，等于自己给自己判卷。
2. **判据写成「质量要好」**，无法判定，最后总是「通过」。
3. **没有最大轮次**，评估者一直说「继续」，永远不结束。

## M5-04 Agentic RAG

**一句话**：把「检索」从固定流水线变成 agent 的一个动作——它自己决定要不要查、查什么、够不够、要不要再查一次。

### 是什么

两种 RAG 的差别：

| | 流水线 RAG | Agentic RAG |
|---|---|---|
| 检索次数 | 固定 1 次 | 0 到 N 次，由模型决定 |
| 查询 | 用户原句 | 可改写、可拆分、可多路 |
| 判断 | 无 | 「这些材料够回答吗」 |
| 成本 | 稳定 | 波动大 |

它解决流水线 RAG 的三个死结：问题需要拆成子问题、第一次没搜到、搜到的材料互相矛盾。

### 怎么运作

```
问题 → 判断：需要检索吗？（常识问题不用查）
 → 拆解：需要哪些方面的材料？
 → 检索（可多路、可换词）
 → 评估：够了吗？有冲突吗？
   → 不够：改写查询再检索（回到上一步，设上限）
   → 够了：基于材料生成，标注来源
```

### 什么时候用它

- 问题复杂、需要多跳（「A 公司去年的营收里，海外占比多少」要先找营收再找地区拆分）。
- 知识库质量参差、需要判断「这条能不能用」。
- 简单单跳问答 → 流水线 RAG 更快更便宜，别上 agent。

判据：**一次检索能不能拿到全部材料？** 能 → 流水线；不能 → agentic。

### 易错点

1. **不设检索次数上限**，陷入「再查一次」的死循环。
2. **不做「够不够」的判断**，检索三轮拿回同一批材料。
3. **成本失控**。每次决策都是一次模型调用，账单会比流水线高数倍。

## M5-05 框架对照

**一句话**：三个框架代表三种世界观——**代码即 agent**（smolagents）、**数据即中心**（LlamaIndex）、**图即流程**（LangGraph）；选型就是选你要把复杂度放在哪。

### 是什么

| 框架 | 核心抽象 | 复杂度落在 | 适合 | 不适合 |
|---|---|---|---|---|
| smolagents | agent = 一段会写代码的函数 | 你的代码 | 学习、原型、工具型任务 | 复杂状态、多分支 |
| LlamaIndex | 索引 / 检索器 / 查询引擎 | 数据管道 | 文档密集、RAG 为主 | 强交互、长流程 |
| LangGraph | 节点 + 边 + 共享状态 | 图结构 | 有分支、需恢复、多角色 | 一次性简单任务 |

### 怎么运作

三者内核仍是同一个循环，差别在「谁拥有控制流」：

```
smolagents：控制流在 Python 里，模型输出代码由解释器执行
LlamaIndex：控制流在查询引擎里，检索→合成是固定管线（可插自定义步骤）
LangGraph：控制流显式画成图，状态在节点间传递，可中断可恢复
```

### 什么时候用它

决策顺序，从上往下问：

1. 需要中断、恢复、人工介入？→ LangGraph。
2. 主要工作是「从大量文档里找答案」？→ LlamaIndex。
3. 只是想让模型会用几个工具、快速验证想法？→ smolagents 或干脆手写。

### 易错点

1. **按 star 数选框架**，不看自己的控制流需求。
2. **在框架里再套框架**，出错时无法定位。
3. **忽视版本漂移**，教程代码半年后跑不通是常态，要锁版本。

## M5-06 微调做函数调用

**一句话**：当工具调用的格式要求极严、又要用便宜的小模型时，专门为 function calling 微调一个小模型，比反复优化提示词更划算。

### 是什么

要解决的具体问题：小模型在「输出严格符合 schema 的调用」上不稳定——字段名错、参数缺失、把调用写成自然语言。微调用「输入 → 标准调用」的成对数据直接把这个行为训进去。

### 怎么运作

```
1. 造数据：真实请求 → 正确的 tool_call（可用强模型批量生成 + 人工抽检）
2. 覆盖边界：不该调的时候不调、参数缺失时追问、多工具时选对
3. 微调：在基座模型上做 SFT（LoRA 通常够）
4. 评测：三个指标——调用正确率、参数正确率、不该调时的误调率
5. 部署：小模型跑工具路由，复杂推理仍交给大模型
```

### 什么时候用它

- 调用量大、格式要求死、成本敏感 → 值得。
- 调用少、工具经常变 → 不值得，工具一变就得重训。
- 大模型本身已经稳定 → 不需要，用提示词 + schema 约束即可。

判据：**工具清单稳定吗？** 不稳定 → 微调是负债。

### 易错点

1. **只训「该调」的样本**，模型变成「见谁都调」。
2. **不测误调率**，上线后整天调不该调的工具。
3. **工具 schema 改了不重训**，模型输出的是旧字段名。
