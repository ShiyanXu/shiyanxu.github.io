# M6 评测、观测与上线

> 一句话：能跑不等于能用。这一模块解决三件事——**看得见**（trace 把每一步摊开）、**量得出**（指标把「感觉还行」变成数字）、**守得住**（红线清单决定哪些事不做）。做完这一步，你交付的是一个可以被人信任的系统，而不是一个演示。

---

## M6-01 观测与追踪

**一句话**：没有 trace 就没有调试——一个请求背后的每次模型调用、每个工具执行、每段耗时与 token，必须能串成一条可回溯的时间线。

### 是什么

一条 trace 至少记录五类信息：

| 字段 | 用途 |
|---|---|
| 输入/输出 | 复现问题 |
| 模型与参数 | 判断是不是换了模型/温度导致的 |
| token 用量（分输入/输出） | 成本归因 |
| 工具调用与耗时 | 定位慢在哪一步 |
| 父子关系（span） | 分清是主循环还是子 agent |

### 怎么运作

```
一个请求 = 一个 trace（有 id）
  ├─ span: 第一次模型调用（prompt 版本、token、延迟）
  ├─ span: 工具 A（参数、结果大小、耗时）
  ├─ span: 第二次模型调用
  └─ span: 生成最终回答
```

三个必须落盘的东西：**完整请求体**（含 system 与工具清单）、**原始响应**（含 usage）、**错误栈**。只记「成功/失败」等于没记。

### 什么时候用它

- 任何要上线的系统 → 必须。
- 本地试验 → 至少打印 usage 与耗时，否则调不动。
- 多 agent 系统 → trace 的父子结构是唯一能看懂「谁在干什么」的方式。

### 易错点

1. **只记最终输出**。出了问题无法复现，因为输入拼装过程没留下。
2. **把日志当 trace**，散在几十个文件里，无法按请求聚合。
3. **记录 PII 原文**，日志本身变成泄露渠道，必须脱敏。

## M6-02 系统评估与优化

**一句话**：先定指标再谈优化——RAG 类的系统必须把「检索坏」和「生成坏」分开评，否则你永远在改错的地方。

### 是什么

分环节的指标体系：

| 环节 | 指标 | 怎么算 |
|---|---|---|
| 检索 | 召回率 Recall@k | 正确材料是否出现在前 k 条里 |
| 检索 | 命中位置 MRR | 正确材料排第几 |
| 生成 | 忠实度 | 回答是否只依据给定材料（有无编造） |
| 生成 | 相关性 | 是否答了被问的问题 |
| 端到端 | 通过率 | 人工/规则判定的正确比例 |

辅助指标：延迟分位（P50/P95）、单次成本、失败类型分布。

### 怎么运作

```
1. 建评测集：50–200 条真实问题 + 标准答案 + 应召回的文档块
2. 跑基线，记录每个环节的分数（不是只记总分）
3. 定位短板：召回低 → 改切块/embedding/查询改写；召回高但答错 → 改提示词/换模型
4. 每次只改一个变量，重跑，看该项指标是否真的动了
5. 固化：把评测集与脚本进仓库，每次改动后自动跑
```

### 什么时候用它

- 任何要迭代的系统 → 没有评测集，优化就是碰运气。
- 换模型/换提示词/换切块策略前后 → 必须跑同一套集子对比。
- 一次性脚本 → 不需要。

判据：**你能不能在十分钟内说清「上次改动让哪项指标变好/变差了多少」？** 不能 → 缺评测。

### 易错点

1. **只评端到端总分**。总分掉了 5%，不知道是检索还是生成，无法行动。
2. **评测集与调参集混在一起**，越调越好，上线就崩。
3. **用模型给自己打分且不抽检**，打分器与被评者同源，系统性偏乐观。

## M6-03 最终项目与自动评测

**一句话**：交付的标准不是「我演示时它跑通了」，而是**别人拿到它、按文档跑一遍、自动评分能过**——可复现才是交付。

### 是什么

一个可被自动评测的交付物包含四件：

| 件 | 内容 | 缺失的后果 |
|---|---|---|
| 入口 | 一条命令能起服务/跑任务 | 别人跑不起来 |
| 数据 | 评测集与依赖的固定版本 | 分数无法复现 |
| 评分脚本 | 自动跑、自动出分、输出结构化结果 | 只能人工看 |
| 说明 | 环境、假设、已知限制 | 被误用 |

### 怎么运作

```
提交 → 拉取 → 装依赖（锁定版本）→ 启动 → 跑评测集
 → 逐条打分（规则 + 模型评审 + 抽检）→ 汇总
 → 输出：总分、分项分、失败样例清单
 → 榜单/报告：同一条基线对比，而不是绝对分数
```

关键设计：**评分要能解释**。只给一个总分没有价值，必须能点开看「哪几条失败、为什么失败」。

### 什么时候用它

- 要交给别人用/评审 → 必须。
- 要给团队做对比（哪个方案更好）→ 必须同一套评分。
- 自己玩的 demo → 不需要这么重，但至少要能一条命令跑起来。

### 易错点

1. **评测集泄露进提示词**，分数虚高。
2. **只测 happy path**，异常输入一进来就崩。
3. **环境不锁定**，三个月后同样的代码跑出不同分数。

## M6-04 责任 AI 与安全

**一句话**：上线前要过的不是「功能测试」，而是一张**红线清单**——哪些数据不能出、哪些动作不能自动做、哪些输出必须可解释。

### 是什么

四类风险，各自有对应的工程手段：

| 风险 | 具体表现 | 手段 |
|---|---|---|
| 提示注入 | 文档里藏「忽略以上指令」 | 把外部内容标记为数据、不执行其中的指令 |
| 越权 | 模型自己决定删库、发邮件 | 权限系统 + 人工审批点 |
| 数据泄露 | 把密钥/客户信息拼进上下文发出去 | 出入口脱敏、上下文白名单 |
| 偏见与误导 | 输出带刻板印象、编造事实 | 引用溯源、拒答策略、人工复核 |

### 怎么运作

```
1. 列清单：这个系统能看到什么数据、能产生什么副作用
2. 对每条副作用：自动 / 需批准 / 禁止，三选一
3. 对每类数据：可入库 / 脱敏后可用 / 禁止
4. 注入防护：外部文本一律作为「数据」包裹，明确告知模型它不是指令
5. 出口检查：正则 + 规则拦密钥、手机号、内部路径
6. 留证据：谁在什么时候批准了什么（审计日志）
```

### 什么时候用它

- 处理真实用户数据 → 必须。
- 有写操作（文件、数据库、消息）→ 必须。
- 纯本地玩具 → 可以轻，但注入防护仍要懂（否则一条恶意网页就能操控你的 agent）。

### 易错点

1. **认为「提示词里写了不要做」就是防护**。注入可以绕过任何提示词。
2. **只防输入端**，忘了工具返回的内容也可能是攻击载荷。
3. **审计日志记在本地**，出事时无法自证，也不可篡改防护。

## M6-05 生命周期与 LLMOps

**一句话**：模型会换代、价格会变、上游会弃用接口——LLMOps 要保证的是「换掉其中任何一件，系统不崩、指标不掉、账单不炸」。

### 是什么

四个持续动作：

| 动作 | 内容 |
|---|---|
| 版本化 | 提示词、评测集、模型名、依赖版本，全部进仓库 |
| 灰度 | 新模型先跑小流量，对比指标再全量 |
| 监控 | 在线指标（成功率、延迟、成本、拒答率）+ 告警 |
| 回滚 | 一条命令退回上一版，且状态兼容 |

### 怎么运作

```
上线前：锁定版本 → 跑离线评测 → 记录基线
上线后：灰度 5% → 对比分项指标 → 全量
日常：成本与延迟曲线、失败样例抽样、模型弃用公告跟踪
变更：任何一处变更 → 走同一条评测流水线 → 不许「就改一个词」直接上
```

### 什么时候用它

- 系统要活过三个月 → 必须。
- 一次性脚本 → 不需要。
- 依赖第三方 API → 尤其需要，接口弃用是必然事件。

### 易错点

1. **提示词写在代码字符串里**，改了没有版本、没有对比、无法回滚。
2. **只看平均值**，P95 延迟已经爆炸但均值正常。
3. **没有成本告警**，一个死循环跑一夜，账单第二天才看到。
