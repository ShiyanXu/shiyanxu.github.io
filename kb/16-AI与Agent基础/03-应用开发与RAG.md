# M3 应用开发与 RAG

> 一句话：这一模块是把模型**接进真实系统**的全部基本功——调通接口、说对话、管好上下文、把外部知识检索进来、把工具交出去。做完这一步，你手里才有一个「能用的东西」；M4 才开始谈「自己能转的东西」。

---

## M3-01 调通一次 API

**一句话**：一次 API 调用就是「发一个消息数组、收一段文本」，所有封装（SDK、LangChain、FastAPI）都只是在这个原语上套壳。

### 是什么

最小调用只需要三样东西：**base_url、api_key、model 名**。请求体的核心是一个 messages 数组：

```python
messages = [
    {"role": "system", "content": "你是一个严谨的技术助手"},
    {"role": "user",   "content": "解释一下 KV 缓存"},
]
resp = client.chat.completions.create(model="...", messages=messages)
print(resp.choices[0].message.content)
```

三层封装，按需要往上走：

| 层 | 形态 | 何时用 |
|---|---|---|
| 原生 SDK | 直接调 HTTP 接口 | 要精确控制参数、流式、重试 |
| 框架封装（LangChain 等） | 统一多厂商接口 | 要快速切换模型、拼链路 |
| 服务化（FastAPI 等） | 包成 HTTP 服务 | 要给前端或其他系统用 |

### 怎么运作

一次请求的生命周期：

```
构造 messages → 发 POST → 服务端排队 → 模型逐 token 生成
  → （流式）边生成边回传 SSE 片段 → 拼成完整回复
  → 返回 usage（prompt_tokens / completion_tokens）
```

工程上必须做的四件事：**超时**（默认值往往太长）、**重试**（指数退避，只重试 429/5xx）、**流式**（长回答不等全套）、**记账**（记录 usage，否则成本无从归因）。

### 什么时候用它

这是所有上层能力的入口。判断「该不该自己封装」的标准：**只用一家模型 → 直接用 SDK**；**要跨厂商切换或做链路编排 → 再上框架**。过早引入框架会在调试时多一层黑箱。

### 易错点

1. **把 key 写进代码或前端**。必须走环境变量或服务端代理。
2. **吞掉错误码**。429（限流）、401（鉴权）、400（参数/上下文超限）处理方式完全不同。
3. **不记 usage**。等到账单爆炸时才发现无法定位是谁在烧 token。

## M3-02 Prompt 工程

**一句话**：提示词不是「咒语」，是**给模型的完整任务说明**——角色、目标、输入边界、输出格式、判定标准，五样少一样它就得猜。

### 是什么

有效提示词的五个部件：

| 部件 | 作用 | 缺了会怎样 |
|---|---|---|
| 角色/场景 | 限定知识范围与语气 | 答得「都对但没用」 |
| 目标 | 一句话说清要产出什么 | 输出跑题 |
| 输入边界 | 只能用哪些材料、不许编 | 幻觉 |
| 输出格式 | JSON / 表格 / 字数 / 字段 | 无法程序化处理 |
| 判定标准 | 什么算好、什么算不合格 | 无法迭代 |

进阶技巧各有明确适用条件，不是越多越好：
- **few-shot**：任务难以描述但容易示范时用（分类、抽取、风格模仿）。
- **思维链**：多步推理、可验证答案时用；简单任务上反而增加错误传播。
- **结构化输出**：要让程序解析时用，配合 schema 约束。
- **让模型先提问**：需求含糊时用，比让它猜要省一轮返工。

### 怎么运作

迭代流程（这是工程，不是灵感）：

```
1. 写最小版本（目标 + 格式）
2. 准备 10–20 条真实输入，跑一遍
3. 标出失败样例，归类失败模式（跑题/格式/编造/漏项）
4. 只针对失败模式加一条约束，重跑
5. 直到失败率稳定；把提示词版本化保存
```

### 什么时候用它

- 任务能用一句话说清且验收标准明确 → 提示词足够。
- 任务需要外部事实 → 先补 RAG（[M3-06](#m3-06-rag-端到端)），别指望提示词。
- 任务需要稳定行为、量大、格式严格 → 提示词 + 输出校验，再考虑微调。

### 易错点

1. **堆砌形容词**（「请非常仔细认真地」）。模型对「具体约束」敏感，对「强调程度」几乎不敏感。
2. **只测一次就上线**。单条成功没有统计意义，至少 20 条看失败率。
3. **用提示词补知识**。把长文档塞进系统提示，既贵又容易在中间段被忽略。

## M3-03 上下文窗口

**一句话**：上下文是**预算**不是仓库——模型能看到的总量有上限，塞进去的每一段都在和别的段抢注意力，也在按 token 计费。

### 是什么

三个必须分清的量：

| 量 | 含义 | 影响 |
|---|---|---|
| 窗口上限 | 一次请求最大 token 数（输入+输出） | 硬边界，超了直接报错 |
| 有效区间 | 模型真正用好的长度，通常远小于上限 | 长文中间部分易被忽略 |
| 成本 | 按输入 token 计费，随长度线性上涨 | 每轮都带上历史 → 平方级累积 |

一个常见误区：窗口 200K 意味着「可以塞 200K」。实际是「可以塞，但中间的信息会被稀释，且每轮都付一遍钱」。

### 怎么运作

四种上下文策略，按成本从低到高：

```
1. 精选：只放与当前任务相关的片段（检索 / 规则筛）
2. 排序：重要的放开头和结尾，次要的放中间（对抗 lost in the middle）
3. 压缩：摘要旧历史、截断工具输出、只留结论
4. 外置：把长内容写进文件/工作区，需要时再读（agent 的做法）
```

再往上就是 [M4-09 Context Compact](04-Agent内核.md#m4-09-context-compact)：把压缩做成自动机制，而不是人工裁剪。

### 什么时候用它

- 单轮问答 → 精选即可，别塞整篇。
- 多轮对话 → 必须决定「保留几轮、怎么摘要」，否则第 20 轮时又贵又糊涂。
- 长任务 → 外置到文件，让模型按需读取（这也是 agent 比聊天强的关键结构差异）。

### 易错点

1. **窗口大就全塞**。成本翻倍、准确率反而下降，是很常见的负优化。
2. **忽略输出也要占额度**。输入塞满上限，输出会被截断。
3. **以为历史越多越连贯**。无关历史是噪声，会诱发跑题。

## M3-04 聊天应用

**一句话**：聊天应用的全部复杂度在**状态管理**——模型本身无状态，是你在每轮把历史重新拼给它。

### 是什么

三个必要构件：

| 构件 | 作用 | 不做的后果 |
|---|---|---|
| 消息历史 | 每轮把 system + 历史 + 新输入拼成 messages | 模型「失忆」 |
| 裁剪策略 | 超长时怎么删/摘要 | 越聊越贵，最终报错 |
| 流式输出 | 边生成边显示 | 长回答时用户以为卡死 |

### 怎么运作

```
用户输入
 → append 到 history
 → history 超预算？→ 摘要最旧的若干轮 / 丢弃工具输出细节
 → 发请求（流式）
 → 收到完整回复 → append 到 history
 → 渲染
```

状态存在哪：内存（刷新即丢）、本地存储（单机可用）、数据库（多端同步）。三者责任不同，**对话状态与会话身份要分开存**。

### 什么时候用它

- 需要多轮追问、需要模型记住前文 → 聊天形态。
- 一次性任务（翻译一段、改一段代码）→ 单轮更省更准。
- 需要「持续对一件事负责」→ 聊天不够，要 [M4-02 Agent Loop](04-Agent内核.md#m4-02-agent-loop)。

### 易错点

1. **把全量历史无限追加**，第 30 轮时单次请求几万 token。
2. **摘要时不保留关键约束**（用户最初的要求），摘要后就跑偏。
3. **system 提示放在历史之后**。位置影响权重，系统约束应始终在最前。

## M3-05 向量检索与向量库

**一句话**：向量检索 = 把「按字面匹配」换成「按意思匹配」，代价是要先切块、算向量、建索引，且切块质量直接决定上限。

### 是什么

一条完整流水线，五步都不能省：

```
1. 加载：PDF/网页/Markdown → 纯文本（保留标题层级）
2. 清洗：去页眉页脚、修断行、统一编码
3. 切块：按语义单元切（标题/段落/代码块），带重叠
4. 向量化：每块算一个 embedding
5. 入库：向量 + 原文 + 元数据（来源、页码、标题路径）
```

### 怎么运作

离线建库，在线检索：

```
离线：文档 → 块 → 向量 → 索引（HNSW/IVF）
在线：问题 → 向量 → 近邻搜索 top-k → （可选）重排 → 返回原文块
```

三个决定质量的参数：
- **块大小**：太大则语义混杂，太小则丢上下文。经验值 300–800 token，带 10–20% 重叠。
- **top-k**：召回太少漏答案，太多引入噪声。常配「先召回 20，再重排取 5」。
- **混合检索**：向量 + 关键词（BM25）并用，专有名词、编号、代码标识符靠关键词才找得到。

### 什么时候用它

判断该不该上向量检索：**用户问题的用词与文档用词不一致，但意思一致吗？** 是 → 需要；不是 → 关键词检索更简单可靠。结构化数据（表格、数据库）不要走这条路，直接查 SQL。

### 易错点

1. **切断了句子**。块内没有完整语义，向量就不代表任何东西。
2. **不存元数据**。没有来源与页码，回答无法溯源，也没法做引用。
3. **换 embedding 模型不重建索引**。向量空间不可比，检索结果等于随机。

## M3-06 RAG 端到端

**一句话**：RAG 是「先检索、再让模型基于检索结果作答」——它解决的是模型不知道和记不住，但**它不保证检索到的东西是对的**，所以溯源与评估不可省。

### 是什么

两条链，必须能分开定位：

```
索引链（离线）：文档 → 切块 → 向量 → 入库
查询链（在线）：问题 → （改写）→ 检索 → 重排 → 拼提示 → 生成 → 附引用
```

四个环节各有典型故障：

| 环节 | 故障表现 | 排查方向 |
|---|---|---|
| 检索 | 找不到相关块 | 切块、embedding、查询改写 |
| 重排 | 找到了但排太后 | 加 rerank 模型 |
| 生成 | 有材料却答错/编造 | 提示词约束「只依据材料」 |
| 引用 | 说不出来源 | 块级元数据缺失 |

### 怎么运作

```
1. 用户问题 →（可选）改写成更适合检索的形式
2. 检索 top-20 → 重排取 top-3~5
3. 拼提示：材料（带编号）+ 问题 + 「只依据材料回答，不足则说不知道」
4. 生成 → 输出时标注 [1][2] 对应材料编号
5. 记录：问题、召回块、回答，供后续评估
```

### 什么时候用它

- 知识在私有文档里、且会更新 → RAG（改文档即可，不用重训）。
- 需要引用与审计 → RAG 天然带来源。
- 知识是「推理能力」而非「事实」→ RAG 无效，该微调或换模型。

判据：**答案是否客观存在于某份材料里？** 是 → RAG；否 → 不要硬套。

### 易错点

1. **用 RAG 治幻觉**。检索错了，模型会自信地基于错材料编，幻觉更隐蔽。
2. **不区分「检索坏」和「生成坏」**，一律改提示词，永远调不好。
3. **只评最终答案不评召回**。召回率不到 60% 时，再怎么优化提示词也上不去。

## M3-07 Function Calling

**一句话**：函数调用是**模型侧的一种输出格式**——它不执行任何代码，只是把「我要调哪个函数、参数是什么」输出成结构化数据，执行和回填全部由你的程序负责。

### 是什么

参与者与职责：

| 角色 | 职责 |
|---|---|
| 你 | 声明工具清单（名字、用途、参数 schema） |
| 模型 | 判断要不要调、调哪个、参数填什么 |
| 你的代码 | 真正执行，把结果作为一条消息回填 |
| 模型（第二轮） | 读结果，生成最终回答 |

关键认知：模型看到的是**工具描述文本**，不是函数体。描述写得含糊，它就会乱调。

### 怎么运作

```python
tools = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定城市的当前天气。用户问到天气、温度、下雨时必须调用。",
    "parameters": {
      "type": "object",
      "properties": {"city": {"type": "string", "description": "城市名，如 杭州"}},
      "required": ["city"],
    },
  },
}]
# 第一轮：模型返回 tool_calls（可能多个）
# 你的代码：执行 → 得到结果
# 第二轮：把结果作为 role="tool" 的消息回填 → 模型给出最终答复
```

### 什么时候用它

- 需要真实数据（天气、库存、数据库）→ 必须调用。
- 需要副作用（下单、发邮件）→ 调用前要人工确认或权限校验。
- 只需要模型自己知道的知识 → 不要加工具，工具越多选错概率越高。

判据：**工具数超过 10 个后，模型选错率明显上升** → 该拆分场景或加路由。

### 易错点

1. **描述写得太短**（「查询天气」）。模型无法判断何时该用，于是该调不调。
2. **参数没约束**。没有 enum/required，模型会编造字段。
3. **以为模型会校验结果**。它只负责下一轮的语言组织，业务校验必须在你的代码里。

## M3-08 多模态与生成

**一句话**：扩散模型的做法是「从纯噪声出发，一步步预测并减掉噪声」，最后剩下的就是图；它和语言模型的共同点是**都在预测，只是一个预测 token，一个预测噪声**。

### 是什么

两条主流路线：

| 路线 | 做法 | 特点 |
|---|---|---|
| 扩散（Diffusion） | 学「加噪的逆过程」，逐步去噪 | 质量高、可控（CFG 强度） |
| 自回归（图像 token 化） | 把图切成 token，用语言模型方式生成 | 与 LLM 架构统一，速度偏慢 |

多模态理解侧则是**把图像编码成向量，与文本向量放进同一空间**（对比学习训练），于是「用文字找图」和「看图回答问题」成为同一个问题的两种问法。

### 怎么运作

```
生成（扩散）：
  随机噪声 → 第 T 步
  → 模型预测「这一步的噪声是多少」→ 减掉一部分
  → 重复 T 次（常见 20–50 步）
  → 得到图像

文本引导：把文字编码成条件向量，每步去噪都参考它；
         CFG（无分类器引导）强度控制「多听话」——太高会过饱和。
```

### 什么时候用它

- 需要配图、示意图、风格化素材 → 生成。
- 需要「按图找相似图」或「用自然语言搜图库」→ 多模态 embedding。
- 需要精确的文字排版、尺寸严格的图表 → 生成模型不可靠，用代码绘图（SVG/图表库）。

判据：**要求像素级精确 → 不要生成；要求创意与氛围 → 生成。**

### 易错点

1. **指望生成模型写对中文文字**。文字渲染仍是弱项，需要后期叠加。
2. **CFG 强度拉满**。过度服从提示反而导致色彩崩坏、构图僵死。
3. **把「生成得像」当成「事实正确」**。示意图里的结构可能完全错误，技术内容必须人工核。

## M3-09 Agent 框架初体验

**一句话**：框架帮你把「循环 + 工具注册 + 状态管理」写好了，代价是你得先接受它的抽象——先用它跑通一个，再回头看 [M4](04-Agent内核.md) 拆开看里面到底做了什么。

### 是什么

三类框架，定位不同：

| 框架 | 抽象 | 适合 |
|---|---|---|
| smolagents | 极简，代码即 agent | 学习、快速验证 |
| LlamaIndex | 以数据/索引为中心 | 文档密集的 RAG 型 agent |
| LangGraph | 以图/状态机为中心 | 流程明确、需要分支与恢复 |

### 怎么运作

所有框架的内核都是同一个循环，差别只在「循环怎么表达」：

```
while 未完成:
    response = 模型(上下文, 工具清单)
    if 没有工具调用: 返回答案
    执行工具 → 结果回填上下文
```

框架额外提供的东西：工具注册与 schema 生成、状态持久化、人工介入点、追踪与回调。这些恰好是 [M4](04-Agent内核.md) 里要逐个手写的机制——**先用框架理解「为什么需要」，再手写理解「怎么做」**。

### 什么时候用它

- 一周内要出 demo → 用框架。
- 需要精确控制每个环节、或要嵌进已有系统 → 直接手写循环（往往不到 100 行）。
- 需要可恢复的长流程 → LangGraph 这类带状态的框架更省事。

### 易错点

1. **把框架的抽象当原理**。换个框架就完全不会了，说明只学了 API。
2. **在框架里调框架**。层层封装后出错无法定位，日志里全是内部调用。
3. **忽略版本**。这类框架迭代极快，教程里的写法半年后常常跑不通。

## M3-10 本地部署与开源模型

**一句话**：本地部署买的是**隐私、离线、可控成本**，付的是**运维与能力折扣**——判断标准不是「能不能跑」，而是「跑起来的那一档够不够用」。

### 是什么

三个决策维度：

| 维度 | 关键量 | 影响 |
|---|---|---|
| 显存 | 参数量 × 每参数字节数（量化后约 0.5–2 字节） | 决定能跑多大 |
| 吞吐 | 每秒 token 数 | 决定能不能多人用 |
| 能力 | 同尺寸开源 vs 闭源差距 | 决定值不值得 |

量化速算：7B 模型 fp16 约 14 GB，4-bit 量化约 4–5 GB；70B 4-bit 约 40 GB——这是单卡能不能碰的分水岭。

### 怎么运作

```
1. 选运行时：Ollama（最省事）/ llama.cpp（CPU 也能跑）/ vLLM（高并发服务）
2. 拉模型：选量化等级（Q4 通常性价比最好，Q8 接近原版）
3. 起服务：暴露 OpenAI 兼容接口 → 上层代码几乎不用改
4. 压测：并发下的首 token 延迟与吞吐
```

### 什么时候用它

- 数据不能出内网 → 必须本地。
- 离线环境（现场、嵌入式） → 必须本地。
- 高频小任务、调用量大 → 本地可能更便宜，但要把运维人力算进去。
- 需要最强能力 → 本地开源一般还差一档，别硬扛。

判据：**把「隐私/离线」和「能力」放在天平上称，如果有第三种方案（脱敏后调云端）通常更划算。**

### 易错点

1. **只看参数量不看量化损失**。Q2/Q3 量化后能力下降明显，不是白拿的。
2. **忽略并发**。单用户流畅不等于能服务一个团队。
3. **忘了上下文长度也吃显存**。长上下文时 KV 缓存能占掉比模型本身更多的显存。
