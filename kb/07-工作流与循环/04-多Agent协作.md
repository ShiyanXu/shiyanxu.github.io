# 多 Agent 协作：四种拓扑与两类风险

> 来源 #25、#8、#24、#44、#45。

## 四种经典拓扑

| 拓扑 | 说明 | 对应实践 |
|---|---|---|
| **Orchestrator-Worker**（编排-执行） | 编排者拆任务、派给执行者 | meta agent + sub agent |
| **Producer-Critic**（生产-评审） | 一写一评 | 「第一个 AI 写、第二个 AI 评」 |
| **Debate / Ensemble**（辩论/集成） | 同一问题多方案并列 | 「3 个 Agent 各出一版 Plan」 |
| **Simulation**（模拟） | 多角色模拟真实系统 | 数百 Agent 模拟社交网络推演 |

## 两类风险

**风险一：同质化（homogenization）**——评审 Agent 次数多了会被同化，评审者逐渐接受被评审者的风格，失去独立性。本质是「共谋」：两个 Agent 互相认可，缺陷被掩盖。

对策：
- 评审用**不同厂商 / 不同模型**；
- 给评审者**独立的评分标准**，而不是让它自由发挥；
- 限制「评审-修改-再审」的轮次，超过就交给人。

**风险二：错误放大**——评审若只是附和，会把错误「盖章确认」，比没有评审更危险。并行方案也不等于正确：三份同质 Plan 只是把同一个偏见复制三份。

对策：
- 要求每个 Agent 先独立给出结论，**不允许看别人的方案**；
- 人工拍板，而不是投票；
- 用可执行的验收（测试、demo）代替「看起来对」。

## 什么时候值得上多 Agent

| 值得 | 不值得 |
|---|---|
| 任务可拆分、子任务之间弱耦合 | 任务小，协调成本大于收益 |
| 需要不同专长（规划 / 编码 / 评审） | 一个模型就能做好 |
| 需要并行缩短时间 | 结果需要强一致 |
| 需要「对抗性」检查 | 只需要执行，不需要判断 |

## 与「主模型只做编排」的关系

多 Agent 的组织形态，与 [多模型分工与编排](../01-Agent心法/02-多模型分工与编排.md) 的「主模型只做分析、编排、验证，实作交给 subagent」是同一件事的两个视角：一个讲**角色**，一个讲**拓扑**。
