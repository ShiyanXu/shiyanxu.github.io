# 费曼精读：用四步法读懂《A Programming Paradigm for Spatiotemporal Composability》

> 一句话结论：这篇论文只做了一件事——把编程语言里**编译期的两个静态保证**（RAII 式的作用域回收、模块导入式的依赖解析）**搬到运行时**，并为"搬到运行时"这件事付清了数学账单。

为什么值得用费曼法读它：它 92 页，其中约 40 页是定义与证明。**顺着读会淹没，用费曼法读不会**——因为你每读一段都要回答"我能不能用一句话说清这段在防什么故障"，答不上来的地方就是你该停下来补的地方。

## 1. 费曼学习法：四步，而不是五个口号

你库里的 [费曼学习法](01-费曼学习法.md) 是五步版（选主题→假装教学→识别空白→回顾简化→持续迭代）。第 1 步和第 5 步是**流程外壳**，真正发生认知变化的是中间三步。读论文时我把它们压成四个动作，因为论文阅读有一个特殊困难：**你不能选主题，主题是别人替你选好的**，你只能选"从哪一段开始暴露自己"。

| 步 | 动作 | 一句话判据 | 读论文时的具体形式 |
|---|---|---|---|
| ① 问 | 先向这段文字提一个"它到底在防什么故障"的问题 | 提不出问题 = 你还没进入这段 | 把标题改写成疑问句 |
| ② 说 | 合上论文，用自己的话讲给一个没读过的人 | 卡壳、含糊、靠术语蒙混 = 盲点 | 写 3–5 句"人话版" |
| ③ 补 | 带着卡壳回到原文的**具体定义/定理/例子** | 补完能指出"哪一行救了我" | 记下定理编号与页码 |
| ④ 减 | 压成一句话 + 一个比喻 + 一张图 | 说不出"如果只记一件事" = 没减成功 | 写"一句话版" |

**为什么这四步对数学论文特别有效**：数学论文的信息密度不在文字里，在**依赖结构**里。你读不懂第 20 页，往往不是第 20 页难，而是第 9 页的某个定义你只是"看过了"而不是"用过了"。费曼法的②会强制你把定义**用一次**，卡壳就暴露在第 9 页。这就是"必要难度"：卡壳不是失败，是定位器。

下面进入正题。每个"站"都走同一套四步，你可以把它当成模板，换成任何论文。

## 2. 逐段精读（九个站点）

### 站 1｜摘要与引言：他到底在修什么 bug（p1、p4–6）

**① 问**（把标题改成疑问句）

- "可组合性"这个词我们天天用，为什么还需要"时间/空间"两个新维度？
- 如果 OS 有进程、K8s 有容器，为什么这两个维度还会缺？
- 作者为什么把"加载/卸载插件"叫 composition，而不是 configuration？

**② 说**（合上论文，我的复述）

> 现代软件越来越需要在**跑着的时候**换零件：IDE 装插件、Agent 换工具、系统自我改造。但换零件有两个隐藏要求：第一，拔掉一个零件后，它留下的痕迹必须能清干净（比如它注册的事件、开的连接、改的全局配置）；第二，零件之间得能说"我需要谁"，并且谁来了/谁走了要能自动开工/停工。
>
> 现在的工程界用粗粒度手段糊弄这两件事：进程重启解决"清干净"，容器编排解决"依赖"。代价是重启丢掉全部内存状态（缓存、连接、半截计算），跨进程通信把本地函数调用变成网络调用。粒度错配——组件是细粒度的，治理手段是进程级的。
>
> 作者的主张：把编程语言里**编译期**就免费拿到的两个保证搬到运行时。静态世界里，"作用域结束自动释放"就是时间可组合性（RAII、bracket），"import 解析"就是空间可组合性。动态世界里没有词法作用域，所以要重新造。

**③ 补**（回到原文，找到救我的是哪几句）

| 我卡在哪 | 原文哪句救了我 | 页 |
|---|---|---|
| "时间/空间"是不是作者硬造的词？ | "In the static setting, temporal composability reduces to lexical scoping (e.g., RAII, bracket patterns), and spatial composability reduces to module import resolution." | 4 |
| 为什么非得是运行时？ | "No fixed lexical scope can delimit a plugin loaded after deployment; no compile-time context can anticipate dependencies that emerge from runtime configuration." | 8 |
| 他说的问题真实存在吗，还是稻草人？ | VSCode 实证：装机量前 100 的扩展里 **87 个含可执行代码**，卸载必须重启 extension host；只有 **7 个**声明了非内置扩展依赖，且 `exports` 返回 `any`，没有结构契约 | 4–5 |
| 为什么 OS/容器不算数？ | 进程级时间保证 + 服务级空间保证，代价是丢进程内状态（重建要秒到分钟）、无法表达同地址空间内的依赖、本地调用变网络开销 | 5–6 |

**④ 减**

- **一句话**：把 RAII 和 import 从编译期搬到运行时。
- **比喻**：静态世界是"写死电路板的电器"，动态世界是"热插拔的设备"——热插拔要求每个接口自带"拔出时自动断电并复位"的机制，还要有"设备在位检测"。
- **如果只记一件事**：这两个维度是**正交**的（时间管"我改了什么"，空间管"我依赖什么"），所以可以分别造机制，最后再合并。

> **这一站的费曼教训**：引言里的数字（87/100、7/100）不是装饰，是**可反驳的锚点**。读引言时问自己"如果这个数字是 10/100，作者的论证还成立吗？"——这一问会让你分清哪些是修辞、哪些是证据。

### 站 2｜预备知识：effect 与 coeffect 的对偶（p7–8）

**① 问**

- effect 和 coeffect 到底是不是"一个东西的两面"？对偶在对偶什么？
- 为什么 monad 对应 effect、comonad 对应 coeffect？
- 这篇论文为什么要花一节讲这些"已知的东西"？

**② 说**（人话版）

> effect 记的是"这段代码**往外写了什么**"：它可能改状态、抛异常、发 IO。类型写成 `Γ ⊢ t : T effect`，那个 effect 注解就是账单。
> coeffect 记的是"这段代码**得从外面读到什么才敢跑**"：需要哪些资源、权限、服务。类型写成 `Γ coeffect ⊢ t : T`，注解在**上下文**上而不是结果上。
>
> 数学上：monad 提供 `η : A → T(A)`（把纯值塞进效果里）和 `μ : T(T(A)) → T(A)`（把嵌套效果压平），正好是"顺序组合"的骨架；comonad 提供 `ε : D(A) → A`（从上下文里取出当前值）和 `δ : D(A) → D(D(A))`（把上下文复制一份给嵌套访问），正好是"依赖上下文"的骨架。`D(X) = E × X` 是"依赖固定环境"的 comonad，`D(X) = ℕ → X` 是"依赖时间流"的 comonad。
>
> 还有一支"graded"流派：用预序半环 `𝒮 = (S, ≤, +, ×, 0, 1)` 给每个变量绑定打刻度——0 表示没用、1 表示线性用一次、n 表示有界、∞ 表示随便用——`×` 组合顺序、`+` 组合并行。

**③ 补**

| 卡点 | 原文位置 | 要点 |
|---|---|---|
| effect 的源头 | Lucassen & Gifford（1986），kinded type system 分 types/effects/regions | 目的是并行程序的调度约束分析 |
| monad 的源头 | Moggi（计算性单子）；Wadler 引入 Haskell | Maybe（部分性）、State（可变状态）、IO（外部交互） |
| coeffect 的源头 | Uustalu & Vene（对称半幺半 comonad）；Petricek et al.（coeffect 作为上下文依赖的统一静态分析） | 捕获 dataflow、属性求值 |
| **本节真正的钩子** | §2.3 最后一段 | 这些系统**全是静态工具**：作用域词法固定、handler 在编译期消解、注解在执行前校验。动态组合要的是"组件来了又走、上下文一直在变"下的同类保证 |

**④ 减**

- **一句话**：effect 是"我欠世界的账"，coeffect 是"世界欠我的货"；前者可退款，后者决定我能不能开业。
- **比喻**：effect = 你在共享白板上写字（要能擦）；coeffect = 你的工位需要哪些插座（插座没通电你就别开工）。
- **如果只记一件事**：这篇论文没有发明新数学，它做的是**换了一种"承载方式"**——把原本写在类型系统里的东西，做成运行时可操作的对象。所以后面所有定义都可以问一句："这个定义，是把哪个静态概念物化了？"

### 站 3｜可回退效应：整篇论文的地基（p9–16）

这是全文最需要慢读的一站。我用它完整示范一次"卡壳→补漏"的循环。

#### 3.1 第一个卡壳：为什么类型是 `Γ → Γ × (Γ → Γ)`？

**① 问**：一个"可撤销的副作用"，最少需要携带什么信息？

**② 我的第一版复述（有错，保留下来当对照）**

> "副作用就是一个函数 `Γ → Γ`，再配一个逆函数 `Γ → Γ`，成对存起来就行。"

**③ 卡壳点与回补**

这个复述错在**把逆元当成全局固定的**。原文（p9）说的是：

> "an effect as a function of type `Γ → Γ × (Γ → Γ)`: applied to the current context, it yields the modified context together with an explicit inverse."

注意返回值的位置：**逆元是被 effect 返回的，不是被调用方预先准备的**。为什么？因为逆元依赖"被作用时的那个状态"——同一个"打开文件"操作，在状态 A 下要关闭 fd 3，在状态 B 下可能关闭 fd 7。所以逆元必须是**逐状态产生的**（per-state inverse，p12 明确列为第一条动机）。

再加一条：**逆元是单边的**（p9）：

> "Undoing is one-sided: what an inverse is held to is `g ∘ f` and never `f ∘ g`."

为什么单边就够？因为恢复只需要"从新状态回到旧状态"。而且现实里很多操作根本不可双边逆：`free` 释放后堆布局回不去，生成一个新名字后那个"新"也回不去（p23 用这两个例子说明为什么后面必须引入观察等价）。**这一条是理解全文的钥匙**：作者从不假装能还原物理世界，他只承诺"回到没人能看出差别的状态"。

**④ 减**：`effect = 变换 + 该变换自己的撤销函数（只对这一次负责）`。

#### 3.2 第二个卡壳：`𝜕Γ` 和那个累加器到底在干嘛？

**定义（p10）**：`𝜕Γ ≔ Γ × (Γ → Γ)`，记作 `(γ, φ)`：`γ` 是当前状态，`φ` 是**累加器**——"到目前为止所有 effect 的逆元的复合"，也就是"把上下文还原到初始态的那个函数"。

**为什么逆元要反序累加？** 看 `track`（Def 3，p10）：

```
track_Γ : (f, g) ↦ (γ, φ) ↦ (f(γ), φ ∘ g)
```

把它读成一句话：**"先用 f 改状态，再把 g 挂到撤销链的末尾"**。因为 `φ ∘ g` 表示"先执行 g 再执行 φ"，所以新挂上去的逆元**最先执行**——这就是 LIFO（后进先出）。为什么必须 LIFO？因为后发生的 effect 可能依赖先发生的 effect 留下的状态；先撤后面的，才能让前面的逆元遇到它当初作用时的那个状态。

**三个定理，各自防一个故障**（这是本节最该背下来的结构）：

| 定理 | 说的是 | 防的故障 |
|---|---|---|
| **Thm 4**（p10） | `pr₁ ∘ track(f,g) = f ∘ pr₁` | 记账不能改变业务行为：`track` 只是顺带记了逆元，正向效果必须和不用 `track` 时一模一样 |
| **Thm 5**（p11） | `track` 是幺半群同态：`track((f₁,g₁)∘(f₂,g₂)) = track(f₁,g₁) ∘ track(f₂,g₂)` | 分批记账 = 一次记完账。否则"边跑边记"和"跑完再记"会得出不同结果，组合性就崩了 |
| **Thm 7**（p11） | 若 `g(f(γ)) = γ`，则 `recover(track(f,g)(γ,φ)) = recover(γ,φ)` | 每一个能自我撤销的 effect，都不移动"恢复的目标"。于是**守恒量** `φ(γ) = γ₀`（soundness invariant），任意多步之后一按 `recover` 就回到 `γ₀` |

`recover`（Def 6，p11）就是 `(γ, φ) ↦ (φ(γ), id)`：用累加器把状态刷回去，再把累加器清空。

**④ 减**：一张图足够。

```
        f₁        f₂             fₙ
   Γ ──────▶ Γ ──────▶ … ──────▶ Γ
   │track     │track           │track
   ▼          ▼                ▼
  𝜕Γ ──────▶ 𝜕Γ ──────▶ … ──────▶ 𝜕Γ ──recover──▶ (γ₀, id)
   φ=id      φ=g₁      φ=g₁∘g₂…   φ=g₁∘…∘gₙ
```

**一句话**：系统只需要维护"一个逆元栈"；加载 = 压栈，卸载 = 出栈并执行。

#### 3.3 第三个卡壳：既然 `track` 够用，为什么还要 `𝔈_Γ`、`⋄`、`effect`、iterator 这一串？

原文（p12）自己给了两条动机，非常实：

1. `track(f,g)` 把 `g` 固定在**参数位**，意味着同一个 `g` 要在所有状态下都满足 `g(f(γ))=γ`。但"撤销"其实只要求在**被作用的那个状态**成立。所以逆元必须能在"看到状态之后"才返回——于是有了 `𝔈_Γ : Γ → Γ × (Γ → Γ)`（输入输出都是"变换 + 逆元"的形状）。
2. `recover` 是**全清**的：它把整个累加器刷掉，不能"只撤其中一个 effect、保留其他"。所以输出侧也要能返回逆元：`𝜕Γ → 𝜕Γ × (𝜕Γ → 𝜕Γ)`，即 `𝜕Γ → 𝜕²Γ`。

于是有了 `effect_Γ`（Def 12，p13）：把 `𝔈_Γ` 提升为 `𝔈_{𝜕Γ}`，即"撤销这件事本身也是一次 effect，它也有自己的逆元"。原文的直觉解释很好：**撤销一个 effect，就是把它的逆元当成一次新的 effect 来跑；而要撤销"这个撤销"，就是把原 effect 再做一次**。这就是 `effect_Γ(e)` 里那个 `track_Γ(g, pr₁∘e)` 的含义。

**这里有一个我必须停下来想十分钟的点（Thm 15，p14–15）**：

> `effect` 并不把 `𝔈*_Γ` 送到 `𝔈*_{𝜕Γ}`；只有当 `g ∘ f = id` 时，下层三角才闭合。

乍看像坏消息：提升一层之后，"带见证的 effect"不再带见证。但读上下文就明白这是**必然且无害**的：

- 累加器被恢复到 `φ ∘ g ∘ f` 而不是 `φ`，只有当 `g∘f = id` 时才相等。
- 但无论等不等，`(φ ∘ g ∘ f)(γ) = φ(γ)` 恒成立——**恢复目标没被动过**。
- 而 Thm 7 需要的恰恰只是`φ(γ)` 不变。

这就是全篇的"证明策略"：**永远不强求比定理需要的更强的性质**。你如果在这里停下来追求"完美可逆"，会卡死；作者的选择是"够用即可"，而"够用"被精确地写成了 `φ(γ) = γ₀`。

**④ 减**：`𝔈*` 是"带质保的 effect"（保证只在自己被作用的状态撤销）；`effect` 是"把撤销也变成一次 effect"；代价是质保只保一层，但守恒量不变。

#### 3.4 第四个卡壳：为什么要 iterator？

`ℑ_Γ ≔ μℑ. Γ → Γ × (Γ → Γ) × Maybe(ℑ)`（Def 17，p15）。三个成分：新状态、逆元、**续延**（Nothing 结束 / Just 下一步）。

因为**一次组件加载不是一个 effect，而是一串 effect**（注册事件、开连接、挂路由……），而且每一步可能要依赖上一步的结果。`Maybe` 续延把"每一步之间"变成一个可插入边界的缝隙——原文明确说这就是 **delimited continuation**，对应主流语言的 `yield`/generator（p16）。

Thm 16（p15）给了那个我们真正关心的结论：**按逆序撤销整串 effect，每个逆元都恰好遇到它自己那次应用产生的状态**。

**④ 减**：加载 = 跑完一个生成器并收集它 `yield` 出来的每个逆元；卸载 = 逆序调用这些逆元。

> **这一站的费曼教训**：卡壳的地方不要跳过，要**写下来**。我上面保留了自己的错误复述（"逆元预先准备好"），因为错误版本恰好能解释后面所有设计的动机。**错误的复述比没有复述有价值得多**——它是你的定位器。

### 站 4｜反应式余效应：依赖怎么变成"自动开关"（p16–21）

**① 问**

- 依赖注入（DI）人人都有，为什么还需要一套数学？
- "响应式"到底响应的是什么事件？
- 为什么 `set` 的逆元是"删掉这个键"，而且要求"这个键原本不存在"？

**② 说**（人话版）

> 把共享环境想成一张**服务注册表** `Σ`：键是接口名（`k : K`），值是实现（`𝒱_k`）。因为不同键的值类型不同，所以 `Σ` 是**依赖类型的偏函数** `(k : K) ⇀ 𝒱_k`——这是它和 `Map<string, any>` 的唯一区别，但这个区别让"取某个键"在类型上就是安全的。
>
> 组件声明一张**钥匙清单** `d ⊆ K`（coeffect specification，Def 21）。系统定义"满足"：`σ ⊧ d ≔ ∀k∈d. k ∈ dom(σ)`（Def 22 前的公式）。每次表变化，系统把这次变化分类成三种：**activating**（原来不满足、现在满足）、**deactivating**（反过来）、**neutral**（没变）。前两种驱动组件的激活/停用，第三种什么也不做。

**③ 补**（三处必须回到原文的细节）

| 细节 | 原文 | 为什么重要 |
|---|---|---|
| `set` 就是 `𝔈*_Σ` | Def 20（p17）+ 紧随其后的那句："`set(k,v)` has type `𝔈*_Σ`, i.e., an effect function on the coeffect context. We can therefore directly apply the effect machinery from Section 3.1" | **两个机制在这里焊死**：注册依赖本身是一次可回退效应，所以"注册/注销"自动获得 LIFO 撤销，不需要第二套机制 |
| 为什么所有变化都能被观察到 | "all mutations to `σ` pass through effect functions (whose inverses recover the previous domain), changes to satisfaction are detectable at each effect boundary" | 反应性的代数基础：**没有旁路写入**，所以"变化"必然经过一个可拦截的边界 |
| 为什么"满足性"就够了 | 三分类只区分"翻不翻转" | 组件的生命周期只由"我能不能跑"决定，不由"值变了多少"决定。这条选择直接导致后面 `target view` 只记 **provider 的 uid** 而不记值（p35、p62） |

**隔离与拦截**（p19–21，很多人跳过，但它解释了真实系统的两个刚需）：

- **隔离** `Σ_iso ≔ (K ⇀ R) × ((r : R) ⇀ 𝒱_r)`：先查"键 → 域（realm）"，再查"域 → 值"。于是同一个键在不同上下文里可以绑不同实现——多租户、测试替身、沙箱都靠它。
- **拦截** `Σ_inter ≔ ((k : K) → ℳ_k) × ((k : K) ⇀ (ℳ_k → 𝒱_k))`：值不再是"值"，而是"元数据 → 值"的**提供者函数**。读取时算 `σ(k)(d(k) ⊕_k ι(k))`，其中 `ι` 是上下文携带的元数据且**右偏**（`ι` 优先），所以外层上下文能约束内层组件怎么用这个依赖，而不用改组件代码（p21 明确指向 §6.3 的权限控制）。

两者在实现上都是**派生（derived）而非原地（in-place）**（Def 23，p19）：不改共享表，只是派生一个子上下文；所以**没有逆元要跑，丢弃子上下文就是撤销**。这个"realization"的区分（denotation 固定、realization 可选）是全文工程感的来源之一。

**④ 减**

- **一句话**：依赖声明是一张钥匙清单；每次有人挂钥匙或摘钥匙，系统就重算一次"你能不能开门"，翻转就自动开/关。
- **比喻**：像机场登机口——不是"我每隔一秒去问一次航班到了没"（轮询），而是"航班状态一变，广播就响"（事件）。三分类就是"登机口从关闭变开放"这个**翻转**本身。
- **如果只记一件事**：`set` 是 effect，所以"注册依赖"和"撤销注册"免费获得了 LIFO 语义——**两个机制不是并列的，是嵌套的**。

### 站 5｜上下文范式与观察等价：把"两个机制"合成"一个世界"（p21–26）

**① 问**

- 前面两套机制各管一个维度，为什么非要合成一个上下文？
- 为什么"经过上下文"还不够，还要限制"绑定值上能做哪些操作"？
- 恢复为什么不能承诺"状态相等"，只能承诺"观察等价"？

**② 说**（人话版）

> 合成后的类型是 `Γ∞ ≔ μΓ. Γ × (Γ → Γ) × Σ`（Def 28，p21）。读法是**俄罗斯套娃的账本**：每一层都有三样东西——当前层状态 `Γ`、这一层的撤销袋 `Γ → Γ`、以及服务注册表 `Σ`。因为 `Γ` 自己又是 `Γ∞`，所以父层可以把"子层的整个生命周期"当成自己的一次 effect 来记账。原文把这个叫 hierarchical composition：父上下文聚合子上下文的效果，加载/卸载在任意层级独立发生（p22–23）。
>
> 光有"一个入口"还不够。组件拿到一个绑定值之后，如果它能对这个值做任意操作（比如直接改对象字段、绕过接口），那"上下文是唯一通道"就是空话。所以每个键携带的不只是值类型，还有**一组操作** `𝒜_k`（Def 29，p21）：`a : X_a → 𝒱_k ⇀ 𝒱_k × (𝒱_k ⇀ 𝒱_k) × B_a`。注意这个形状：**参数、新值、逆元、结果**——操作的前两个成分本身就是一个带见证的 effect function，第三个是 outcome。于是"对值的操作"自动获得可撤销性，而且被**限定在这一个键上**（`a_Σ` 的 lift 只读写信 `k`，别的键原样不动，p22）。

**观察等价**（这是全篇最容易被读者当成"技术性补丁"、实际上最深刻的一节，p23–26）：

> 如果"恢复"要求状态**相等**，那这个理论第一天就死了：`free` 不会把堆布局还原成 `malloc` 之前的样子；生成一个新名字之后，撤销"生成"也不会让"下一个名字"变回同一个。所以作者把等号换成 `≃`：**两个状态等价，当且仅当没有任何观察者能区分它们**（Def 31）。
>
> 观察者能看到什么？**能看到这个键的操作，以及操作产生的结果**。所以 `≃_k` 由"测试"生成：一个测试是一串有限的操作序列（正向和逆元都算），两个值不可区分，当且仅当每个测试在两边要么都无定义、要么都定义且结果相同。Lemma 32 说这是**最粗的**、被所有操作尊重的等价关系——于是它同时是"定义"和"证明原则"（要证两值等价，只需给出一个被操作尊重、且包含这对值的等价关系）。

**③ 补**（这一节三个必须记住的技术点）

| 技术点 | 位置 | 作用 |
|---|---|---|
| `≃_S`：忘记 `S` 之外的键 | Def 33（p24） | 一个组件的正确性只在**它自己声明的键**上被检查，别的键上的差异与它无关。这是"局部保证"能被形式化的关键 |
| 把 `=` 全部换成 `≃` 后定理仍成立 | Lemma 38（p25） | §3.1 的每个等式在 `≃` 下依然成立，证明只用到"传递性 + 被尊重"两条性质。所以前面那套推导不是白做的 |
| 函数上的 `≃` 不是自反的 | Def 34 后的讨论（p25） | `f ≃_S f` 要求"相关输入给相关输出"，这正是"尊重等价"的条件。所以"尊重"是**要证的**，不是白给的 |

**④ 减**

- **一句话**：恢复不是把世界还原成一张照片，而是还原成"没有任何观察者能看出差别"的状态。
- **比喻**：酒店退房不是把房间恢复成"你入住前的分子排列"，而是"下一位客人查不出你住过"——床单换了、垃圾清了、账单结了。`≃` 就是"查不出"的精确定义。
- **如果只记一件事**：`≃` 不是妥协，是**接口设计的自由度**——你发布的 outcome 越少，测试越少，`≃` 越粗，可交换的操作就越多。这条在 §3.4.2 立刻被兑现成一条设计规则。

### 站 6｜独立性：凭什么可以乱序拔插（p26–31）

**① 问**

- Thm 16 已经保证"逆序撤销能回到起点"，为什么还需要"任意顺序"？
- 两个组件的 effect，什么条件下互不干扰？
- 为什么"交换性"要写进接口（作为 witness），而不是让使用者去猜？

**② 说**（人话版）

> Thm 16 的场景太理想：它假设"从我开始到我撤销，中间没人动过状态"。真实系统里，你撤销的时候，别的组件早就往同一个上下文里写过东西了。这时你的逆元遇到的是一个**被别人挪动过的状态**，它还能不能只撤回自己那一份？
>
> 答案取决于**交换性**：如果"你的每个动作"和"我的每个动作"都能交换顺序，那我可以把你插进来的动作一个个"挪开"，直到我的逆元重新遇到它当初作用的状态。注意"每个动作"包括**正向和逆向的交叉**（`f₁` 对 `g₂`、`g₁` 对 `f₂` 都要交换）——因为撤销时你遇到的是别人的正向结果，而别人的逆元也可能插进你的正向序列里。
>
> 形式化（Def 40、42，p26–27）：给一个 iterator `i`，先取它所有可达的续延 `reach(i)`，再用"每个可达迭代的正向映射 + 它在每个状态产生的逆元"生成一个**变换幺半群** `𝔐(i)`。两个 iterator 独立，当且仅当 (1) `𝔐(i)` 与 `𝔐(j)` 逐元素交换；(2) 谁的动作都不改变对方"会产出什么逆元、走哪条续延"。
>
> 结论（Thm 43，p28）：若 `e₁…eₙ` 两两独立，则**按任意排列**应用它们的逆元，都能回到 `γ₀`。

**③ 补**（三个让我"啊哈"的地方）

| 点 | 原文 | 意义 |
|---|---|---|
| 只需在生成元上验证交换 | Lemma 41（p27） | "与 `𝔐(j)` 全部元素交换"的函数构成子幺半群，所以检查生成元就够。这条把"无穷多对映射"降成"有限几对" |
| 为什么 clause (2) 不能省 | Def 42 第 2 条 + Thm 43 证明中的 claim (2) | 光有映射交换不够：还要保证"后面那些 effect 在别人动过的状态上产出的逆元，和原来一样"。否则你以为手里拿的是 `gᵢ`，其实是另一个函数 |
| 独立性 ≠ `e₁⋄e₂ = e₂⋄e₁` | p27 末段 | 后者只比较两条复合路径的端点；前者要求**每个**变换与**每个**变换交换。后者弱得多，撑不起 Thm 43 |

**④ 减（本节是全篇最实用的工程结论，值得单独记）**

> 能不能乱序拔，取决于"插座的插拔是否互不干扰"；而这个"互不干扰"由**提供者**写进接口（Def 46 的 witness），**不靠使用者猜**。

**Coeffect 交换性三个例子**（p29–30，重点，因为它们把抽象条件变成了可执行的设计规则）：

| 键的形态 | 是否交换 | 为什么 | 现实对照 |
|---|---|---|---|
| **登记表**（路由、事件监听） | ✅ 交换 | 每次注册拿一个**新 id**，逆元删掉那个 id，两次注册永远指向两个不同条目 | CRDT 给每次添加打唯一 tag 正是这个原因；而"裸元素集合"的增删就不具备这个性质 |
| **有序链**（中间件） | ❌ 不交换 | 插在前面和插在后面，下游看到的请求不同；任一顺序都不能在不影响对方的前提下撤出 | Koa/Express 中间件顺序敏感 |
| **分配器** | 看接口 | 若句柄不被任何操作比较（opaque），则两次分配可交换（`≃` 把句柄重命名视为等价，和 CompCert 的做法一致）；若地址是**被比较的 outcome**，则不交换 | POSIX：`mmap` 可返回任意空闲地址、`creat` 可给任意 inode，所以可交换；而 `open` 必须返回**最小可用 fd**，这一条要求就让两次分配不可交换 |

这段还引出了"scalable commutativity rule"（p29–30）：**把交换性理解为"通过接口不可区分"，而不是"内部状态相等"**，于是"少发布一个 outcome"就能把某个键从"不交换"挪到"交换"——这是接口设计的自由度，也是站 5 那个 `≃` 的直接回报。

**Theorem 47**（p30）把结论抬到组件级：只要两边的 provision 不相交（`P₁∩S₂ = P₂∩S₁ = ∅`），且它们共同出现的键都交换，两个 context-mediated iterator 就独立。**于是"键级交换性"这一个义务，撑起了"组件级独立性"这整个结论**。

### 站 7｜演算与元理论：九条规则，五个保证（p31–56）

**① 问**

- 数学机制有了，但"一个真实系统在跑"这件事怎么写成可证明的对象？
- 为什么需要"目标视图"和"已提交视图"两份状态？
- 那五个定理，各自在防哪种真实事故？

**② 说**（人话版，分三层）

> **第一层：对象。** 组件是三元组 `(d, p, e)`（Def 48，p31）：`d` 我要求哪些键、`p` 我可能提供哪些键、`e` 我激活时跑的 effect iterator。组件被实例化成 **fiber**（Def 49，p31–32）：`⟨d, p, e, π, σ, τ, θ⟩`——多了父指针 `π`、自己的表 `σ`、退休标志 `τ`、生命周期状态 `θ`。`θ` 有四个值：`Inactive`、`Reloading(i, g, ω)`、`Active(g, ω)`、`Unloading(g, ω)`，其中 `g` 是累加器、`ω` 是**已提交视图**（激活时解析到的"每个键由哪个 fiber 提供"）。
>
> **第二层：规则。** 全部动作只有九条（§4.2，p34–38，Figure 1）：三条**编排**（`O-Insert` 插入、`O-Retire` 打退休标记、`O-Remove` 真正移除）+ 六条**生命周期**（`L-Begin` 开始激活、`L-Iter` 走一步、`L-Finish` 落地、`L-Divert` 中途转向、`L-Leave` 决定停用、`L-Unload` 执行撤销）。编排规则是**外部输入**（只有编排者能插入/退休），生命周期规则是**系统自己会走的**（前提满足就走，不需要调度器）。原文特意强调：规则是**反应式而非调度式**的——没有任何规则提到调度器，所以"对所有序列成立的定理"自动对所有调度策略成立（p37）。
>
> **第三层：状态机。** 每个 fiber 反复做一件事：把"我**应该**是什么样"（`target`，由当前状态算）和"我**注册时**是什么样"（`committed`，`ω`）比较，不等就朝目标迁移。`target_n(γ)`（Def 53，p35）= 退役或依赖不满足则为 `⊥`，否则是 `k ↦ provider_k(γ)`。`quiet(γ)` 表示所有 fiber 都停在目标上，没有迁移在飞。

**③ 补**（这一节信息量最大，只列"读懂必须抓住的六个机关"）

| 机关 | 位置 | 它解决的具体事故 |
|---|---|---|
| **`target` 记 provider 的 uid，不记值** | Def 53 + p62 | 两个 fiber 提供**相等**的值时，若按值比较就看不出"换人了"。uid 永不复用，所以"替换"必然被检测到；反过来，同一 provider 原地覆盖自己的值则**不触发**重载（p63 明说这是有意的） |
| **`committed view` 在激活时锁定，卸载最后才丢弃** | p35、Alg 5 的 Line 14/28 | 组件拆自己时，常常还需要读那个"正在被撤走"的依赖（关连接池要把连接还给 provider）。锁定视图让它"整个拆解期间都能读到" |
| **`¬relied_n` 这道 guard** | Def 54、`L-Unload` 前提（p36–37） | 提供者不能先跑，否则消费者拆到一半发现依赖已经没了。guard 把"撤销绑定"推迟到"所有解析过它的消费者都已卸载"之后 |
| **guard 为什么不会死锁** | p37 + Thm 73 证明 | 关键在 `σ_γ` 只取 **ACTIVE** fiber 的表的并集：一个进入 `Unloading` 的 fiber 立刻"不再提供"，于是**没有新的消费者能再依赖它**，依赖图只减不增，所以 guard 必然释放 |
| **一次迁移不能跨越两个解析** | Thm 71（p48） | 迁移是分步的，中间可能别人的依赖变了。`L-Iter`/`L-Finish` 的前提要求 `target = ω`，一变就 `L-Divert` 出去。所以"激活过程中用的依赖解析"始终是同一个 |
| **`confinement`** | Def 55（p38） | 每个规则只能读写"自己声明的两个表 + 自己的表"，不碰别人的控制字段。这是能把九条规则列成 Table 1（"每条规则写了什么"）的前提，否则定理的 case analysis 无从下手 |

**§4.3 各小节给出的保证，一一对应真实事故**（p43–55；共七个定理/推论）：

| 定理 | 形式 | 防的事故 |
|---|---|---|
| **Thm 64 保型**（p43） | 注册表四条良构性（父指针落地、provision 两两不相交、`ω` 在 `d` 上全定义且值在注册表内、`ω` 指向的 fiber 已安装）被每条规则保持 | 系统自己把注册表搞坏（悬空父指针、两个 fiber 抢同一个键） |
| **Thm 68 恢复精确**（p46） | 在某 fiber 的"任期"内，把它在 `γ_u` 处执行累加器，结果等价于"把期间别人的那些步骤从 `γ_b` 直接执行一遍" | 卸载一个组件时，误伤别人写进去的状态 |
| **Cor 69 终态归零**（p46） | 任期结束时该 fiber 的表为空 → 满足 `O-Remove` 的前提 | 卸载后残留绑定，导致后续无法重新插入 |
| **Thm 70 顺序**（p47） | 激活只在依赖满足时开始；且"提供者先于消费者激活、晚于消费者退出"（`b < b'`、`u' < u`） | 消费者用到一半，提供者先跑掉 |
| **Thm 71 解析一致**（p48） | 一次激活期间的每次迭代都跑在**同一个** `ω` 上；若中途目标变了，要么正常落地，要么 `L-Divert` 转去卸载（二选一） | 一次激活的前半段和后半段用的是两套依赖（"混用新旧解析"） |
| **Thm 73 进展**（p49–51） | 不死锁（不静止就必有规则可用）+ 有界终止（`S(n) ≤ (K+3)(V(n)+1)`），前提是 `≺` 无环、迭代长度有界、名字集合有限 | 系统卡在某状态，谁都不动 |
| **Thm 80 合流**（p51–55） | 无论你按什么顺序插入/卸载，只要最终配置一样，静止态**唯一**（mod 名字重命名） | "动态折腾过的系统"和"从零加载最终配置的系统"行为不一致——这是最难、也最值钱的保证 |

**④ 减**

- **一句话**：每个插件都在"该开/该关"与"已开/已关"之间自己走路；系统只保证三件事——走路不互相踩脚、踩了也能各自退回去、最后停的地方唯一。
- **比喻**：Thm 80 就是"事务最终一致性"的版本：中间怎么增删改都行，只要最终配置相同，读到的就是同一个状态。原文自己给的类比是**增量计算与从头计算的协调性**（p51）。
- **如果只记一件事**：**这条定理是"动态组合"能被称为"组合"的全部理由**。没有它，"运行时拼装"只是一个实现技巧；有了它，你才可以像读静态代码一样推理一个动态系统——"组件作者只需推理静止态"（p55）。

### 站 8｜实现与边界：92 页数学压成一个 API（p57–77）

**① 问**

- 这么多定义，落到代码里是哪几个函数？
- 理论里的状态和代码里的状态怎么对上？
- 作者自己承认哪些地方"没保证"？

**② 说**（人话版）

> **一个原语**：`ctx.effect(callback)`。所有对上下文的修改都必须走它；它跑一个生成器（每次 `yield` 出一个逆元），把逆元折成一个 LIFO 的 `dispose`，并且（1）**自毁**（`armed` 标志，保证 dispose 最多跑一次、且能中断在飞的迭代），（2）**挂到父上下文的 dispose 上**（子 effect 的逆元本身是父上下文的一次 effect）——这两条正好对应 §3.1 的 `track` 与 `𝜕²Γ`（Alg 1，p59）。
>
> **三个槽**：`@@store`（值表 `σ`）、`@@isolate`（键→域 `ρ`）、`@@intercept`（键→元数据 `ι`）。`ctx.get` 是 `σ(ρ(k))`；`ctx.set` 是 effect，返回删键的逆元，并在装/卸时都调 `notify`（Alg 2，p60）。`notify` 遍历所有活 fiber，凡是"声明了这个键且解析到同一个域"的，就 `refresh` 一次——这就是 Def 22 的三分类在代码里的样子（Alg 3，p61）。
>
> **一个状态机**：`ctx.use` 把一个组件实例化成 fiber，并且**这个实例化本身是父 fiber 的一次 effect**（callback 里 `refresh`，逆元里把 `target` 置 `⊥` 并 `unload`）——所以"父卸载时子自动级联"是免费的（Alg 4，p61–62）。`refresh` 重算 `target`，不等就起一个 `reload` 或 `unload` 任务；`reload` 先 `committed ← resolve(inject)`，跑完 `apply` 后再比一次 `target`，变了就**链式**转 `unload`；`unload` 先 `await` 所有被通知的依赖者到 `INACTIVE`，再跑 `dispose`，跑完再看 `target`，若是新目标就**链式**转 `reload`（Alg 5，p62–63）。这个"惯性"（inertia）就是 §4.4 说的**只走 `L-Divert` 的落地分支**。
>
> **一个加载器**：配置树的每个 entry 记录 `id / url / isolate / intercept / config / disabled`，恰好是 `(τ, π, d, p)` 的镜像（Def 81，p65）。改哪个字段就做最小动作：改 `config` 交给组件自己 diff，改 `disabled` 就是卸载/重载，改 `isolate` 要重算域（用 delimiter 判断"这个绑定是不是我自己的"，Alg 7，p66–67）。
>
> **一个 HMR**：模块替换不需要开发者写 accept 边界，因为 **fiber 本来就是效果边界**——丢掉旧 fiber 就撤销了它装的一切，新 fiber 重新装一遍（§5.2.2，p67–68）。三个阶段：分类（Alg 8）→ 找过期条目（Alg 9）→ 事务式重载（Alg 10，失败则回滚缓存）。

**③ 补**（必须回到原文看的三处"作者自曝"）

| 自曝 | 位置 | 含义 |
|---|---|---|
| **witness 不被运行时检查** | §5.1.1（p59） | "逆元真的能撤销"和"同键操作真的交换"这两件事，运行时不验证，是**组件作者的义务**。定理依赖它们，但实现信任它们 |
| **系统边界** | §6.1（p70–71） | 一个位置"在边界内"当且仅当：系统**独占**修改它、且能**恢复**修改前状态。否则该操作等于 `id_Γ`（既不记录也不撤销） |
| **获取 vs 发射** | §6.1（p71） | `open` 装一个描述符（**获取**，在边界内，可撤销）；`write` 把字节推出去（**发射**，跨边界，`id_Γ`）。发射只能靠**延迟提交**（output commit）或**补偿**（saga，用应用定义的更粗的等价），而补偿的交换性需要**重新证明**，不能沿用本文的定理 |

**④ 减**

- **一句话**：作者把 92 页数学压成了四个 API：`ctx.effect`（记账）、`ctx.get/set`（依赖）、`ctx.use`（实例化）；剩下全是这三者的组合。
- **比喻**：`ctx.effect` 是"带存根的收据本"——你每做一件事就撕一张存根，退款时按存根倒序退。
- **如果只记一件事**：**理论的强项变成了实现的弱项**。理论说"恢复是结构保证"，实现说"逆元对不对是你的事"。读这篇论文时要一直分清"哪句是定理、哪句是契约"。

### 站 9｜相关工作：三分钟看清"它到底新在哪"（p77–82）

**① 问**：如果只看 §7，这篇论文的"新"能压缩成一句什么话？

**② 说**：作者把前人分成两大阵营，各自有四种/三种做法：

| 维度 | 前人做法 | 代表 | 与本文的差别 |
|---|---|---|---|
| **时间** | ①状态向前迁移（DSU/HMR） | Kitsune、Erlang `code_change`、webpack/Vite HMR | 需要手写迁移函数；本文是"撤回 + 重装"，不需要迁移代码，但组件的内存状态不跨重载存活 |

| | ③静态作用域内自动反转 | STM、Janus、RCCS、线性类型/RAII | 反转范围**预先固定**；本文不预设作用域，按组件生命周期撤 |
| | ④运行时代理记录回收 | Nooks、shadow drivers、Akeso | 平台决定"能记录什么"，组件只能用平台已知的资源；本文允许组件自定义 effect 并自带逆元 |
| **空间** | ①初始化期接线 | Spring/Guice/Angular、Vue `provide/inject`、React Context | 提供者被替换/移除时**不重解析**，依赖者既不重启也不重载 |
| | ②可用性反应 | OSGi Declarative Services、iPOJO、R-OSGi | 回收靠**手写且同步**的回调；本文是"撤销累积效果 + 异步拆解跑完再动" |
| | ③值级反应 | FRP/signals（Solid、Vue、Angular） | 粒度是"值"，无异步生命周期语义；本文是"组件"粒度，且只保证"一次迁移不跨两个解析"，不保证 glitch freedom |

**最接近的三个工作**（审稿人一定会问，必须抓住）：

- **Effekt**（Brachthäuser et al.）：把 effect 类型当 capability。差别在目的（模块化解释 vs 追踪与回退）和时机（静态类型 / 词法作用域 vs 运行时 / 任意生命周期）。
- **Heunen et al. 的 dagger arrows**：形式化上最接近"可逆效应"。差别在**可逆性住在哪里、要求多强**：他们是范畴层面的**全局可逆 + 双边逆**；本文是运行时的**逐 effect 单边逆**，组合出来的逆由复合得到。
- **Nooks / Akeso**：系统层最接近"代理式回收"。差别在**记录范围由平台固定**，而本文让组件自己声明 effect 与逆元。

**④ 减**

- **一句话**：别人在**编译期 / 平台层 / 单组件**给保证；本文在**运行时 / 组件粒度 / 任意交错**给保证。
- **如果只记一件事**：这篇论文的"新"不是新数学，是**证明了"这套运行时语义"能把局部保证抬成全局保证**——Effekt 有 capability，Heunen 有可逆性，OSGi 有依赖反应，但没人把这三件事合起来并证明合流。

## 3. 一次完整闭环演练：从"看不懂 Thm 43"到"能讲给别人"

前面九站是"讲解"，这一节是**演示过程**。挑全文最容易卡住的一个点，把我真实的四步走一遍。你可以拿它当模板。

### 第 1 步（问）：把定理改写成疑问

原定理（p28）：

> Let `e₁,…,eₙ ∈ 𝔈*_Γ` be pairwise independent and applied in order from `γ₀` … Applying the `n` inverses at the state the sequence reaches, **in the order of any permutation** of `{1,…,n}`, reaches `γ₀`.

我的疑问：**"任何排列"凭什么？** Thm 16 已经说"逆序"能回去，那不就是唯一正确顺序吗？为什么这里敢说**任意**顺序都行？如果任意顺序都行，那"顺序"这个概念还有什么意义？

### 第 2 步（说）：第一版复述（说出来才发现漏洞）

> "因为两个 effect 独立，所以它们可以交换，交换就能换顺序，所以任意顺序都行。"

**这个复述是错的**，而且错得很典型：它把"交换性"当成了"顺序无关"，但定理要求的是**更强的交叉交换**（正向对逆元也要交换）。我在第二句就说不下去了——"那为什么还要正对逆、逆对正都交换？"——这就是盲点。

### 第 3 步（补）：带着具体问题回原文

我给自己提了三个更小的问题，逐个回原文找答案：

1. **为什么"逆序"不够？** → 因为逆序只保证"每个逆元遇到它自己那次应用产生的状态"（Thm 16 的场景）。而 Thm 43 的场景是：我在状态 `γₙ` 处执行 `g₁`，此时别人的 effect 还留在里面。所以 `g₁` 遇到的不是 `γ₀`，而是 `f₂(f₃(…fₙ(γ₀)))` 之类。
2. **那 `g₁` 怎么还能工作？** → 用交换性把它"推"过去。证明里的 claim (1)：`g_j(δ_u) = δ'_{u}`——先把 `g_j` 穿过它后面的所有正向映射，直到它遇到 `f_j(δ_{j-1})`，再用 witness `g_j(f_j(δ_{j-1})) = δ_{j-1}`。**"穿过"这个词是关键**：交叉交换（`g_j` 对 `f_i`，`i>j`）就是允许穿过。
3. **为什么还要 clause (2)？** → claim (2)：后面的 effect 在"被别人动过的状态"上产出的逆元，必须和在原状态上产出的一样。否则你手里拿的 `gᵢ` 已经不是当初那个函数了，`g_j` 能穿过的对象就变了。**这一条是"交换映射"之外必须单独要求的东西**——第一次读时完全忽略了它。

补完之后我的复述变成：

> 独立性 = "你的任何动作和我的任何动作都能互换位置，而且换位置不会让我少拿或多拿一个逆元"。有了这两条，我就可以把别人的动作从我自己的撤销路径上**一个个挪开**，直到我的逆元重新遇到它当初作用的状态。因为每次挪开都不改变结果，所以**先挪哪一个都行**——这就是"任意排列"。

### 第 4 步（减）：压成比喻 + 一句话

- **比喻**：两个人在同一张账本上记账。只要他们的笔迹**互不覆盖**（交换），并且合账时**谁的字都还在**（不干扰产出），那么核对账目的顺序就随便——先核谁的都行。
- **一句话**：**独立性把"顺序敏感"局部化了**：只要你的动作和我的动作互不覆盖，我的撤销就不需要你配合。
- **可删与不可删**：Thm 43 的证明细节（向下归纳、`δ'ᵤ` 的构造）可以忘；但"clause (1) 交换 + clause (2) 不干扰产出"这两条**必须记住**，因为它们是"能不能乱序卸载"的唯一判据，也是 §4.3.2 把局部结论抬到全局的支点（Lemma 66 就是用它证明"任何执行序列都两两独立"）。

### 这个演练暴露的三条通用规律

1. **卡壳几乎总在"为什么需要这个更强的条件"**。这时不要问"它是什么"，要问"如果删掉它，哪个证明会断"。删掉 clause (2) → claim (2) 断 → `g_j` 穿不过去。**定位到"哪个证明会断"，就定位到了它的功能。**
2. **错误复述要留着**。我第一版复述把"交换"等同于"顺序无关"，这个错误恰好对应一个真实误解（也是很多工程文档里的误解）。**改对之后的版本，正好是对这个误解的纠正**——这就是可分享的知识。
3. **数学论文的"减法"必须减到判据级**。"独立性就是互不干扰"没用；"互不干扰 = 映射交叉交换 + 产出不受影响"才有用，因为它可验证。

## 4. 把费曼法做成一套可复制的流程

### 4.1 四步法：问 — 说 — 补 — 减

| 步 | 你具体做什么 | 完成判据（不合格就别往下走） | 常见糊弄方式 |
|---|---|---|---|
| **① 问** | 把每个小节标题改写成 1–3 个疑问句；疑问必须指向"它防什么故障/它解决什么反例" | 问题里出现"为什么必须""如果不这样会怎样"这类**可被证明反驳**的形态 | 写成"什么是 X"（这是查词典，不是提问） |
| **② 说** | 合上原文，写 3–5 句人话；要求：不出现原文的专有名词，或每个专有名词都先用一句大白话定义 | 一个没读过该领域的人能听懂，并能反问一个有意义的问题 | 用术语解释术语（"因为它是幺半群同态，所以……"） |
| **③ 补** | 对每个卡壳，回到**具体位置**（定义/定理/例子/脚注），记下"哪一行救了我" | 能说出"如果没有这条，第 X 页的证明会断在哪一步" | 只回看摘要和引言，然后"感觉懂了" |
| **④ 减** | 写"一句话 + 一个比喻 + 一张图"；再写"如果只记一件事" | 这句话能独立成立，不需要上下文；比喻能预测一个新情况 | 把原文抄短（压缩 ≠ 简化） |

**四步之间的关系**不是流水线，是**螺旋**：④ 产生的比喻常常在下一段失效，失效本身就是新的 ①。这种感觉不舒服是正常的——**"必要难度"就是学习正在发生的信号**。

### 4.5 八种失败模式与纠正

| 失败模式 | 症状 | 纠正 |
|---|---|---|
| **术语搬运** | 笔记里全是原文名词，没有一句人话 | 强制规则：每个术语第一次出现必须配一句大白话，否则删掉 |

### 4.6 分享给别人的 15 分钟讲稿（骨架）

1. **钩子（1 min）**：一个真实故障——"VSCode 卸载一个插件为什么要重启整个 extension host？前 100 个扩展里 87 个都得重启。"
2. **两个维度（2 min）**：时间（拔掉要能还账）、空间（依赖要能自动响应）；静态世界的对应物是 RAII 和 import。
3. **一个机制（4 min）**：effect = 变换 + 自己的撤销函数；系统 = 撤销栈；卸载 = 出栈。**现场画那张 `track/recover` 图**。
4. **另一个机制（3 min）**：依赖 = 钥匙清单；变化 = 三分类；翻转 = 开关。
5. **合并的代价与回报（3 min）**：恢复只能是"观察等价"（free/malloc 的例子）；换来的是"任意交错的组件可以像静态拼装一样推理"（合流定理）。
6. **收尾（2 min）**：这套东西落成了 Cordis，四个 API；边界在哪（发射不可撤销、witness 靠自觉）。

**提问模板（苏格拉底式，用来带别人，而不是灌别人）**：

- "如果删掉这个条件，哪个证明会断？"（逼他定位功能）
- "这个机制在防哪种具体事故？举一个你见过的。"（逼他从抽象回到场景）
- "它的做法和 X 差在哪？如果 X 也能做到，这篇论文还剩什么？"（逼他建立坐标系）
- "你能举一个这套理论会失效的场景吗？"（逼他找到边界）
- "用一句话说，而且这句话要能被反驳。"（逼他做减法）

### 5.2 全文压缩（背这五句就够讲清）

1. 动态组合缺两样保证：卸载能还账（时间）、依赖能自动响应（空间）。
2. 还账靠"每个 effect 自带单边逆 + 累加器按 LIFO 撤销"，且记账与组合同态。
3. 响应靠"声明依赖集合 + 每次变化三分类 + 状态机迁移"。
4. 两者合成一个上下文，用"观察等价"作真理标准，于是只要组件间"互不干扰"（独立性）就能任意交错。
5. 于是"怎么折腾都等价于从零加载最终配置"（合流）——这就是"可组合"的真正含义。

### 5.3 三个我仍然觉得值得追问的问题（诚实标注）

1. **witness 靠作者自觉**：Thm 68 依赖"逆元真的能撤销"，但运行时只信不查。那么大规模生态（4000+ 插件）里，这个假设的实际违约率是多少？作者没有测量。
2. **发射不可撤销**：`write` 出去的字节、`send` 出去的消息，理论只能"延迟提交"或"补偿"，而补偿的交换性要重新证明（p71 自己承认）。这意味着 §3.4 的定理在最需要它的场景（对外部世界的副作用）恰好不适用。
3. **单一 realm 的简化**：§4.1 用"provision 两两不相交"换取形式化简洁，代价是"一个有非空 provision 的组件同一时刻只有一个 fiber"（p33）。多实例组件（比如每个租户一个数据库连接池）要靠 broker 或 realm 扩展绕过去——这是理论到产品的真实缝隙。
