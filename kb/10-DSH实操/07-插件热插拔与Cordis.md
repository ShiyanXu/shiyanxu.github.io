# 插件热插拔与 Cordis：文件出现，能力就在

> 结论：**DSH 的 Harness 可以在「不重启、不重装」的情况下增删能力。** 这不是便利性，而是一种架构选择。

## 一个可复现的实验

1. 在 `~/.dsh/skills/hello-dsh/SKILL.md` 写一个技能（输出一句暗号）；
2. 在会话里说「hello dsh」，它读文件、输出暗号；
3. **不重启**，直接 `rm -rf ~/.dsh/skills/hello-dsh`；
4. 再说一次，它说：无法再从本地文件读出那句暗号了。

它这一轮明明「见过」那句暗号（就在上文），但它判断**那不算数**——暗号的来源是磁盘上的文件，而文件没了。

5. 把文件写回去，依然不重启，暗号又回来了。

**文件出现功能就在，文件消失功能就没了，中间没有任何重启、安装、注册的动作。**

对比熟悉的软件：装浏览器插件要重启浏览器，装 VSCode 扩展要重载窗口。

## 轨迹里能看到什么

一次「hello dsh」的完整执行轨迹（灰字）：

| 轨迹行 | 谁干的 |
|---|---|
| Context injection · dsh-system-prompt | system-prompt 插件注入系统提示 |
| Context injection · skill-catalog | tool-skill 插件注入技能清单 |
| Skill · hello-dsh | tool-skill 提供的加载工具 |
| Read · .../SKILL.md | tool-fs 插件 |
| Think · ... | agent-loop 插件驱动的推理 |

**插件列表告诉你「有什么」，这几行告诉你「它们怎么协作」。**

注意 `Read` 那一行：它不是「想起」了什么，是**打开文件读的**。这也是为什么 `description` 比正文重要——模型先只看到「名字 + 一句描述」的清单，正文要等它决定用了才读。

## 为什么能做到：Cordis 的时空可组合性

DSH 建在 Cordis 框架上，对应论文《A Programming Paradigm for Spatiotemporal Composability》（Yifan Shi、Wei Zhang、Tianyi Cui，北大与 DeepSeek-AI）。它把「动态组合」拆成两个维度：

**时间维度**：组件被移除时，它对环境的修改必须被**完整撤销**。做法是每次改动自带一个撤销操作，运行时全程追踪，卸载时按相反顺序执行。

论文给了一组对照数据：VSCode 安装量前 100 的扩展里，**87 个含可执行代码，禁用或卸载必须重启整个扩展宿主**；而声明了 `extensionDependencies` 的只有 7 个。

**空间维度**：组件声明它需要什么，运行时在依赖出现、消失、换提供者时重新判断它能不能跑。**依赖不满足时组件静默不激活，不报错。**

## 对排查的直接价值

「插件装了但没反应」的第一排查方向，就是空间维度：**依赖没满足，它压根没激活，所以不报错。**

依次检查：
1. 依赖的插件/服务是否在运行；
2. 声明的依赖名是否与实际提供者一致；
3. profile 是否装对了（不同 profile 的插件互不干扰）；
4. 看轨迹里的 context injection 行，确认清单里有没有它。

## 对「Harness 工程」的意义

大多数 Harness 是「装好就不能动」的：想加一个工具、换一套提示词，要么重启，要么改代码重新部署。

DSH 把 Harness 本身做成了**可热更新的组合体**：能力是文件、插件是零件、循环在运行时被替换。这带来两个实际后果：

- **试验成本低**：写一个技能文件就能试，删掉就回滚；
- **故障边界清楚**：能力消失通常不是「模型变笨」，而是「文件/依赖不在了」。
