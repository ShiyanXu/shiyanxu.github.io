# Harness 工程精读：从可靠单次到自动循环

> 结论：这套笔记把课程的 14 讲按"问题"重排成 10 篇。读法不是顺着讲次背概念，而是遇到哪类失败，翻到对应的一篇，照着示例改仓库。

## 这套笔记解决什么

课程原结构按"讲次"推进：先讲模型为什么不可靠，再讲仓库、指令、状态、范围、验证、可观测、交接，最后两讲进入 loop 和 graph。它适合从头学，不适合遇到问题时查。

这里按**失败类型**重组：

- agent 说做完了但没做完 → 第 6 篇
- 新会话接不上 → 第 4、8 篇
- 指令越写越长、关键约束被忽略 → 第 3 篇
- 同时改很多东西、没有一个跑通 → 第 5 篇
- 不知道问题出在哪一层 → 第 1 篇
- 想让它自己持续跑 → 第 9、10 篇

每篇保持同一结构：结论 → 核心概念 → 关键要点 → 落地示例 → 操作清单 → 常见误区 → 关联 → 来源。示例统一用一个假想的 `TaskFlow`（FastAPI + PostgreSQL 任务管理应用）串起来，便于对照。

## 逐讲一句话

| 讲 | 核心论断 |
|---|---|
| L01 | 同一模型在裸环境和完整 harness 下产出差两个数量级；失败先归因，再决定换不换模型。 |
| L02 | Harness 是指令、工具、环境、状态、反馈五个子系统，缺一个都不完整。 |
| L03 | 不在仓库里的知识等于不存在；用五个问题验收仓库地图。 |
| L04 | 巨型指令文件挤占上下文、埋没关键约束；入口是路由器，不是百科全书。 |
| L05 | 上下文一定会满，跨会话一定会丢；用进度、决策、git 检查点重建。 |
| L06 | 初始化和实现是两种任务；先建环境、测试、启动契约、任务清单，再写功能。 |
| L07 | 同时开多条线会同时造成过度延伸和不足完成；WIP=1 是默认安全值。 |
| L08 | 功能清单是 harness 原语；每项必须有行为、验证命令、状态，状态由外部门控。 |
| L09 | agent 系统性过度自信；完成判定必须外部化，按三层闸门逐层验。 |
| L10 | 单测对组件边界系统性盲视；涉及跨组件时，端到端跑通才算完成。 |
| L11 | 可观测性分运行时和过程两层；合同、评分表、追踪让"感觉不对"变成可修的缺陷。 |
| L12 | 熵增是默认方向；构建、测试、进度、工件、启动五条同时满足才算可以交接。 |
| L13 | `/goal` 是最小 loop；六原语、maker/checker 分离、四种沉默成本决定它能跑多远。 |
| L14 | 图把 loop 里的隐式决策显式化；节点、边、状态、路由四件套，五个判据决定要不要画。 |

## 怎么用这套笔记

1. **当诊断手册**：先看第 1 篇的五层归因，再跳到对应篇。
2. **当改造清单**：每篇末尾的"操作清单"可以直接逐项做。
3. **当模板库**：配置索引里的文件复制到目标仓库，改占位符，不要在本库路径下运行；批量迁移用 [sync-agent-config.ps1](配置/scripts/sync-agent-config.ps1)。
4. **当检索入口**：frontmatter 里有 `title`、`category`、`generated`、`tags`，按 `category: Harness工程/*` 或 `tag: harness` 可以筛出全部。

## 维护约定

- 新增笔记沿用同一结构，文件名 `NN-主题.md`，编号决定阅读顺序。
- 课程原文更新后，先核对对应篇的"来源"，再改内容，不要只改结论。
- 配置文件和笔记分开放：`笔记/` 只放解释，`配置/` 只放可复制工件。
- 每篇的"落地示例"必须能落到具体命令或文件，不写"加强管理"这类空话。
- 生成时间统一记录在本批次的 `generated` 字段；单篇大改时更新该篇时间。
