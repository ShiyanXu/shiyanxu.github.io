# 智能体优先的仓库：把工程纪律从代码挪到结构上

> 三名工程师五个月不手写一行代码，交付约一百万行、合入约 1,500 个 PR 的产品。结论不是「模型够强」，而是：人不再写代码之后，仓库本身成了产品——文档、边界、约束与反馈回路的密度，决定智能体能不能跑到终点。

## 起点：空仓库，第一行代码也不是人写的

2025 年 8 月下旬，首次提交落在一个空的 Git 仓库上。仓库结构、CI 配置、格式化规则、包管理器设置、应用框架，由 Codex CLI 带着 GPT-5 参照一小套现有模板生成；连告诉智能体该怎么在仓库里干活的 `AGENTS.md`，也是 Codex 自己写的。

五个月后：约一百万行代码（应用逻辑、基础设施、工具、文档、内部开发者工具），约 1,500 个 PR 被打开并合并，推动这一切的是三名工程师，人均每天 3.5 个 PR；团队扩到七人后吞吐量反而还涨。总耗时约为手写代码的 1/10——产品在数百名内测用户手里跑着，有人每天用，也经历过上线、部署、故障和修复。

工程师这个角色被抽掉了核心动作：

- 重点转向系统、架构和杠杆。早期进展慢，不是 Codex 能力不够，而是环境规范不够明确：缺工具、缺抽象层、缺内部结构。
- 工作方式变成深度优先：把大目标拆成更小的构建模块（设计、代码、评审、测试），先让智能体建出这些模块，再用模块去解锁更复杂的任务。
- 卡住时「再努力一点」不再是答案，唯一有效的问题是：还需要什么能力，怎么让这个能力对智能体既清晰可读、又可强制执行？人几乎只通过提示交互——描述任务、跑智能体、允许它开 PR。

## 应用的可读性：连 QA 都要变成智能体可读

吞吐量上去后瓶颈换成了人工 QA。人的时间与注意力固定，方向只能反过来——让 UI、日志、指标本身对 Codex 直接可读。

- **能跑起来**：应用可按 git worktree 启动，Codex 为每次改动起一个实例；Chrome DevTools 协议接进智能体运行时，配一组处理 DOM 快照、截图、导航的技能，它就能复现错误、验证修复、直接推理界面行为。
- **能查到数**：日志、指标、追踪走一套本地可观测性堆栈，每个工作树一份临时实例，任务结束连日志带指标一起删；Codex 用 LogQL 查日志、PromQL 查指标。

提示词因此能写成可验证的验收条件，而不是形容词：「确保服务启动在 800ms 内完成」「四条关键用户旅程中任何跨度都不得超过两秒」。单次运行连续六小时以上很常见，通常发生在人睡觉时。

**这就是 README、文档、单文件可读性在智能体优先时代更重的原因：读者换人了。** 人类读者能靠上下文补齐、能问同事；智能体只读得到运行时情境里的东西。原文没单独给 README 立规矩，但等价物很清楚——`AGENTS.md` 当入口，`docs/` 当正文，判据只有一条：智能体能不能在仓库里读到它。

## 仓库是记录系统，不是档案柜

情境管理是让智能体扛大任务时最难的一关。最早的教训很朴素：**给它一张地图，不是一本一千页的说明书。**

团队先试过「一个巨型 `AGENTS.md`」，失败了，四条原因值得抄下来：

- **情境是稀缺资源**。巨型指令文件会挤掉任务、代码和相关文档，智能体要么漏掉关键约束，要么针对错误的约束做优化。
- **指导一多就失效**。什么都「重要」等于什么都不重要，智能体退化成局部模式匹配，而不是有意识地导航。
- **它会立刻腐烂**。庞杂手册最终是过期规则的坟场，人一停止维护，它就变成很有吸引力的麻烦源头。
- **它没法机械核实**。覆盖率、新鲜度、所有权、交叉链接，单个大文件都查不了，漂移必然发生。

改法是把 `AGENTS.md` 当**内容目录**：约 100 行，注入情境，主要作用是地图，指向别处更深的真实来源。知识库落在结构化的 `docs/` 里：

```text
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/     index.md、core-beliefs.md
├── exec-plans/      active/、completed/、tech-debt-tracker.md
├── generated/       db-schema.md
├── product-specs/   index.md、按产品领域拆分
├── references/      design-system-reference-llms.txt、nixpacks-llms.txt、uv-llms.txt
├── DESIGN.md  FRONTEND.md  PLANS.md  PRODUCT_SENSE.md
└── QUALITY_SCORE.md  RELIABILITY.md  SECURITY.md
```

- 设计文档编目并索引，带验证状态，另有 `core-beliefs` 定义智能体优先的操作原则；架构文档给域和包分层一张顶层地图，一份高质量文档会给每个产品领域与架构层打分并追踪差距。
- **计划是一等工件**：小改动用临时轻量计划，复杂工作写成执行计划，带进度和决策日志，一并提交进仓库；活跃计划、已完成计划、已知技术债集中版本化，智能体不依赖外部情境就能跑。
- 结构实现的是**渐进式披露**：从一个小而稳定的入口切入，被明确告知下一步去哪查。

而且不靠自觉：专职 linter 和 CI 作业校验知识库是否更新、是否交叉链接、结构是否正确；定期跑的 doc-gardening 智能体扫描不再反映真实代码行为的过时文档，直接发修复 PR。

## 目标是智能体的可读性

仓库完全由智能体生成，第一优化目标就是**它对 Codex 的可读性**——和让新人能上手一个模块是同一件事，只是读者更苛刻。

判据很硬：**智能体运行时情境里拿不到的东西，等于不存在。** 知识留在 Google Docs、聊天记录或人脑子里，系统就访问不到；代码、Markdown、schema、可执行计划这类仓库本地、已版本化的工件，才是它能看到的一切。团队里那次让所有人对齐架构模式的 Slack 讨论，智能体发现不了，处境就跟晚三个月入职的新人一样。

- 优先选能完全内化进仓库、在仓库里可推理的依赖和抽象；被称为「枯燥」的技术反而更好建模——可组合、API 稳定、训练集里见得够多。
- 有时让智能体重写一个功能子集，比绕开公共库里不透明的上游行为更便宜。例：没引 `p-limit` 那类通用包，而是自研带并发的 map 辅助函数，与自家 OpenTelemetry 仪表紧耦合、100% 测试覆盖、行为完全符合运行时预期。

命名、目录、依赖方向、可发现性，能落到 linter 和结构测试里的就落进去；只写在文档里靠自觉的，等于没有。

## 架构与品味：管不变量，不管实现

**靠强制不变量、而不是微观管理实现，让智能体跑得快又不掏空地基。** 典型例子：要求 Codex 在边界处解析数据形状，但不规定用哪个库（模型自己偏爱 Zod，团队没有指定）。

更重的一层是架构。智能体在有严格边界和可预测结构的环境里效率最高，于是整个应用围绕一个严格模型搭建：每个业务域切成固定几层，层序固定为 `Types → Config → Repo → Service → Runtime → UI`，只能「向前」依赖，依赖方向被严格校验，只允许有限的一组边；横切关注点——认证、连接器、遥测、功能标志——只能通过唯一显式接口 `Providers` 进入，其余路径一律不允许。

这套做法通常要等到几百名工程师才值得上；对编码智能体而言它是**早期前提**：有了约束，速度才不会掉，架构才不会漂。

落地手段是自定义 linter 加结构测试，再配一小撮「品味不变式」：结构化日志、schema 与类型的命名约定、文件大小上限、特定平台的可靠性要求。因为这些 lint 是自研的，错误信息里可以直接写修复指令，注入智能体情境。边界感分两处：中央强制边界、正确性和可重复性，边界之内给团队和智能体很大的表达自由。生成的代码不总符合人类风格偏好，这没关系——只要正确、可维护、对下一次智能体运行清晰可读，就算达标。

人的品味不会消失，只是换了通道：评审评论、重构 PR、面向用户的 bug，会被记成文档更新，或者直接写进工具；文档说不清的地方，就变成代码。

## 吞吐量改变了合并的理念

Codex 吞吐量上来之后，一批传统工程规范直接失效。这个仓库刻意把阻塞式合并门减到最少：PR 生命周期很短；测试偶发失败通常靠后续重跑解决，而不是无限期卡住进展；人类可以审 PR，但并非必须，评审大量改成智能体对智能体。

背后的账很简单：**智能体吞吐远超人类注意力时，纠错成本低，等待成本高。** 同样的策略在低吞吐环境里是不负责任的，在这里通常是对的。

| 维度 | 低吞吐（人力主导） | 高吞吐（智能体主导） |
|---|---|---|
| 合并门 | 尽量多、尽量严 | 尽量减少阻塞 |
| PR 生命周期 | 长，反复打磨 | 短（原文只给「短」，未给行数阈值） |
| 偶发失败 | 阻塞到查清 | 后续重跑 |
| 评审 | 人逐行看、必须批准 | 智能体自审 + 智能体互审，人可选 |
| 主要成本 | 返工与缺陷 | 等待 |

## 「智能体生成」到底意味着什么

说的是**整个代码库**。原文列的产出范围：产品代码与测试、CI 配置与发布工具、内部开发者工具、文档与设计历史、评估框架、审阅评论与回复、管理仓库本身的脚本、生产仪表板定义文件。

人一直在场，只是抽象层次变了：优先处理工作、把用户反馈翻译成验收标准、验证结果。智能体遇阻时不被当成「模型不行」，而被当成信号——识别缺了哪样东西（工具、指导与约束、文档），补进仓库，修复仍由 Codex 自己写。它也直接用标准开发工具：拉评审反馈、行内回复、推更新，经常自己压缩并合并 PR。为了把 PR 推完，团队让 Codex 先在本地审自己的改动，再在本地和云端拉特定审查智能体，对人和智能体的反馈逐条响应，循环到所有审查方满意——本质上是 Ralph Wiggum 循环。

## 自主水平是爬上去的

自主性不是开关，是把越来越多开发环节编码进系统的结果：测试、验证、审查、反馈处理、恢复。这个仓库跨过的那道门槛，是 Codex 能端到端驱动一个新功能——一句提示，它能验证仓库当前状态 → 复现已报告的漏洞 → 录一段演示故障的视频 → 实施修复 → 跑起应用验证修复 → 录第二段视频演示解决 → 开 PR → 回应智能体和人类反馈 → 检测并修复构建故障 → 只在需要判断时交回人类 → 合并。

原文同时给了冷水：这个行为很大程度上依赖该仓库的具体结构和工具，没有同等投入，不能假设它可以泛化——至少现在还不行。

## 熵与垃圾回收

完全自主带来新问题：**Codex 会复现仓库里已有的模式，包括那些不均衡、不够理想的。** 时间一长必然漂移。

起初靠人顶：每周五（占一周的 20%）清理「AI 残渣」，显然不可扩展。后来把「黄金原则」直接编码进仓库，再配一套循环清理流程。所谓黄金原则，是带主观意见的机械规则，目标只有一个——让代码库对未来的智能体运行仍然可读、一致。两条样本：优先用共享工具包而不是手写辅助函数，把不变式集中管理；不做「YOLO 式」数据探测，要么验证边界，要么依赖类型化 SDK，别让智能体基于猜出来的结构往上盖。

后台定期跑一组 Codex 任务，扫描偏差、更新质量等级、发定向重构 PR，多数一分钟内能审完并自动合并。这更像垃圾回收：技术债是高息贷款，持续小额偿还好过攒到某天一次性剧痛。人的品味一旦被捕捉住，就会持续作用于每一行代码；不良模式当天被发现和清掉，而不是传播数天乃至数周。

## 仍在学习

架构连贯性在一个全智能体生成的系统里长期怎么演化，人类判断力在哪一步回报最高、又怎么把这种判断力编码进系统，模型继续变强之后这套系统会变成什么样——这三件都还没有答案。

已经清楚的是：造软件仍然需要纪律，只是纪律从代码挪到了支撑结构上，工具、抽象、反馈回路的分量越来越重。团队当前最棘手的挑战也在这一侧：设计环境、设计反馈回路、设计控制系统。
