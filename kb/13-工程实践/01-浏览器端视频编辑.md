# 案例：浏览器端视频编辑的技术选型

> 素材来源：#75，一次真实的 AI 辅助架构评估。全批内容里**唯一一段完整的技术选型过程**。

## 提问

> 「帮我分析一下 jimila/baocut-app，如果我要用浏览器——WebAssembly(Rust)，从浏览器端渲染视频，不经过服务端，可行性如何？如果可行帮我写一个技术方案。」

## 结论

**值得做，但要把「浏览器预览」与「浏览器导出」分开。**

| 目标 | 可行性判断 | 建议 |
|---|---|---|
| 时间线图文、字幕、几何动画导出 | 高，适合作为第一段 | 优先复用现有 WASM 渲染核心 |
| 视频合成 + 字幕/背景音乐、本地导出（1080p） | 可行，但需要完善的媒体处理管线 | 作为首个正式产品目标 |
| BCF 动画文档直接在浏览器导出 | 可行，但首段代码复杂度高 | 单独处理 BCF 渲染入口的宿主依赖 |
| TSX 输入直接生成动画 / 视频 | 需要同时覆盖编辑与浏览器内核 | 不要与第一段媒体导出混在一起 |

## 架构分工

- **Rust / WebAssembly 负责「调度」**：时间线运算、动画采样、文字排版和画面合成；
- **WebCodecs 负责浏览器端本地的音视频编解码**；浏览器文件接口负责「取素材、写出成片」。

因此可以做到：**素材不上传、渲染不经过服务器，也不要求用户启动本机的 `bcut._serve`。**

方法论提示：先统一**输入模型（timeline JSON / BCF / TSX）**，再决定哪些能力进 WASM 核心、哪些走 WebCodecs；**性能敏感路径优先落 Rust**。

## 最小技术方案骨架

```
输入层   : Timeline JSON / BCF / TSX  →  统一为内部 IR
调度层   : Rust + WASM（时间线运算、动画采样、排版、画面合成）
编解码层 : WebCodecs（VideoEncoder / AudioEncoder）+ 文件接口取素材/写成片
预览层   : Canvas / WebGL 实时低分辨率预览
导出层   : WebCodecs 硬件编码 1080p，分批处理避免主线程阻塞
资产层   : 全部本地，不上传；无需后端渲染服务
```

## 背景知识

**WebAssembly（WASM）**：可移植的二进制指令格式，让 C/C++/Rust 编译产物在浏览器沙箱中以接近原生速度运行。视频编辑场景的价值是把**计算密集的时间线运算与画面合成**放到 WASM，避免 JS 主线程阻塞。

**WebCodecs API**：浏览器原生音视频编解码接口（VideoDecoder / VideoEncoder / AudioDecoder / AudioEncoder），可直接调用硬件编解码器。它让「在浏览器里合成并导出视频」第一次变得可行且高效——这是整个方案的关键支点。

**为什么预览与导出要分开**：

| | 预览 | 导出 |
|---|---|---|
| 核心诉求 | 低延迟、可交互 | 高保真、可长时间运行 |
| 实现 | WASM + Canvas/WebGL 实时渲染 | WebCodecs 硬件编码 |
| 分辨率 | 可降低 | 目标分辨率（如 1080p） |
| 主要风险 | 掉帧 | 内存、编码稳定性、主线程阻塞 |

两者对延迟、内存、精度的要求不同，混在一起会两头不讨好。

**Rust + WASM 的组合优势**：Rust 无 GC、内存安全、可编译到 WASM，适合做媒体处理管线（像素级操作、时间线运算）。
