# 从一次选型里提炼的方法：怎么让 AI 做架构评估

> 素材来自 #75 的真实对话。本篇不复述结论（见 [浏览器端视频编辑](01-浏览器端视频编辑.md)），只提炼**可复用的提问与验收方法**。

## 一次好的技术选型，AI 做了什么

1. **先溯源**：读仓库的提交记录与代码结构，而不是凭模型名猜测项目能力；
2. **划边界**：明确声明「这是 API 层面的可行性评估，没有实际跑构建和性能测试」；
3. **给分层结论**：不是「可行 / 不可行」，而是「哪部分先做、哪部分后做、哪部分别混在一起」；
4. **指出待验证项**：需要原型验证的环节单独列出。

## 提问模板

```
背景：<谁用、什么场景、约束是什么>
目标：<要达成什么，不许做什么>
问题：<具体到技术方案，不要问「这个方向怎么样」>
要求：
1. 先读 <仓库/文档>，说明你依据了哪些事实；
2. 给出「可行 / 有条件可行 / 不建议」的判断，并说明前提；
3. 把方案拆成阶段，标出每阶段的验证方式；
4. 明确指出你没有验证、需要原型验证的部分。
```

## 验收一份 AI 技术方案的四条标准

| 标准 | 不合格的表现 |
|---|---|
| **有事实依据** | 只谈「通常」「一般来说」，没有引用具体代码/文档 |
| **有前提条件** | 「可行」但不说在什么条件下可行 |
| **有阶段划分** | 一上来就给完整架构，没有最小可验证路径 |
| **有不确定性声明** | 把推测说成结论 |

## 常见误区

1. **问「哪个技术更好」**：正确的问法是「在我的约束下，哪个更合适」。
2. **不给约束**：没有约束，模型只能给通用答案（呼应 [交代全局上下文](../03-提示词工程/01-交代全局上下文.md)）。
3. **一次问太大**：把「选型 + 架构 + 实现」拆成三轮，比一轮问完更可靠。
4. **不做小验证**：任何「可行」在跑通最小 demo 之前都只是假设。

## 与「两头理论」的对应

技术选型本身就是一次 Plan：**先出方案、比较、再动手**。区别只是这里的「多个架构师」变成了「多次提问 / 多个模型」。
