# AGENTS.md：给 Agent 的项目上下文文件

> 素材来源：一份相册里的 `AGENTS.md` 长图，以及「把原型规则写进 `Agents.md` / `claude.md`」与「文档先行」两处讨论。这类文件在不同工具里叫 `AGENTS.md`、`CLAUDE.md`、`.cursorrules` 等，作用相同。

## 它解决什么问题

每次新开一个会话，Agent 对项目一无所知：用什么语言、代码放哪、测试怎么跑、什么不能碰。没有这个文件，你就得每轮重复交代——这正是「提示词工程」应升级为「上下文工程」的地方。

## 截图里能看到的结构

原图是一份真实项目的 `AGENTS.md`，可见部分包括：

- **最高指令 / 总则**（优先级最高的约束）；
- **语言规则**（用什么语言回复、代码注释用哪种语言）；
- **项目上下文的读取顺序**（先读哪个文件、再读哪个目录）。

配套的还有一张手机相册里的缩略图，与原图同源。

## 一个可用的骨架（建议模板）

> 以下为按上述结构整理的通用写法，不是截图原文。按项目实际情况删改。

```markdown
# AGENTS.md

## 最高指令
1. 不确定时先提问，不要猜。
2. 修改前先读相关文件，不要凭记忆改。
3. 破坏性操作（删文件、改 schema、force push）必须先确认。
4. 本文件与用户即时指令冲突时，以用户指令为准。

## 语言规则
- 回复用中文，代码注释用英文。
- 提交信息遵循 Conventional Commits。

## 项目上下文（按顺序读取）
1. `README.md` —— 项目是什么
2. `docs/architecture.md` —— 模块边界
3. `docs/conventions.md` —— 代码规范
4. `package.json` / `pyproject.toml` —— 命令与依赖

## 常用命令
- 安装：`pnpm i`
- 测试：`pnpm test`
- 只跑单测：`pnpm test -- <file>`

## 不要做
- 不要新增依赖，除非说明理由。
- 不要改动 `migrations/` 下已合并的文件。
```

## 写法要点

| 要点 | 说明 |
|---|---|
| **短** | 只写「模型猜不到」的信息；能读代码得到的，不要写 |
| **可执行** | 「用 pnpm」而不是「尽量使用现代包管理器」 |
| **有优先级** | 明确冲突时谁听谁的 |
| **分层** | 全局规则放根目录，子目录可放局部 `AGENTS.md` |
| **可维护** | 命令变了就更新，否则它会变成错误信息的来源 |

## 该写什么、不该写什么

这类文件每次运行都会进上下文，所以它的价值几乎完全取决于写得准不准——不是「听起来对」的通用最佳实践，而是**基于真实观察到的 Agent 行为**。

| 写 | 不写 |
|---|---|
| 必须用的框架、库、设计模式 | 长篇通用文档 |
| Agent 反复踩的已知坑 | AI 生成的、与实际系统不符的指导 |
| 输出期望（「简短」「只给代码」） | 一次性偏好、极少用到的细节 |
| 团队自己的约定 | 塞得过满的指令（把上下文搞脏） |

另外一定要写清 build / test / lint 命令，否则 Agent 得自己猜怎么跑。

代码库、架构、规范、流程变了就跟着更新。因为指令每次都在上下文里，小改进会被放大：少一次重复错误，就少一串被浪费的 token。成本视角见 [AI 用量成本优化](../08-模型与推理/06-AI用量成本优化.md)。

## 与 Skill 的区别

- `AGENTS.md`：**项目内常驻**，讲「这个项目是什么、怎么跑」；
- Skill：**按需加载**，讲「这类任务怎么做」，可跨项目复用。

两者配合的方式：`AGENTS.md` 里写「遇到 X 类任务时使用 Y Skill」。

## 与原型驱动的关系

把「做新功能前先改本地原型」这条规则写进 `AGENTS.md` / `claude.md`，Agent 就会默认先动原型、确认后再改功能。**规则写进文件，才不依赖人的记性。**
