# 有效上下文的构成：把注意力预算花在刀刃上

> 结论：**好的上下文工程不是「写更长的提示词」，而是找到最小的一组高信号 token。** 这是 Anthropic 对「上下文」给出的工程定义。

## 两个概念的分界

| | 提示工程（Prompt Engineering） | 上下文工程（Context Engineering） |
|---|---|---|
| 对象 | 指令怎么写（尤其系统提示） | 推理那一刻窗口里到底有什么 |
| 范围 | 一次性 | 每一轮都重新策展 |
| 包含 | 提示词 | 系统指令、工具、MCP、外部数据、消息历史、文件 |
| 时代 | 单次分类/生成任务 | 多轮、长时间跨度、会自我累积的智能体 |

**上下文 = 采样时进入模型的那组 token。** 上下文工程就是在模型的硬约束下，优化这组 token 的效用。

## 为什么它是有限资源：上下文腐化

- 「大海捞针」式基准揭示 **context rot**：窗口内 token 越多，模型准确召回的能力越差。
- 原因是架构性的：Transformer 让每个 token 关注所有其他 token，n 个 token 就有 **n² 条成对关系**；长度一长，注意力被摊薄。
- 模型的注意力模式来自训练数据，而训练数据里短序列远多于长序列——**模型对「全局依赖」的经验本来就少**。
- 所以这是**性能渐变，不是断崖**：长上下文仍可用，但检索精度与长程推理会下降。

一句话：**上下文有「注意力预算」，每个新 token 都在消耗它。**

## 系统提示词的「恰当高度」

两种常见失败：

| 失败 | 表现 | 后果 |
|---|---|---|
| **太具体** | 用 if-else 式的硬编码逻辑去「逼出」精确行为 | 脆弱、难维护 |
| **太笼统** | 只说「你要专业、要严谨」，假设了并不存在的共享上下文 | 模型没有可用信号 |

恰当高度在两者之间：**具体到能引导行为，抽象到能当启发式**。

写法建议：
- 用分区（`<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description`）或 Markdown 标题切开；
- 先拿最小版本在最强模型上跑，**按失败模式加指令和例子**，而不是预先穷举；
- 格式本身在变得不重要（模型越来越强），**信息是否完整才重要**。

## 工具：少而清楚

- 工具是「智能体与信息/行动空间之间的契约」，要**返回 token 高效的信息**，并鼓励高效行为。
- 常见失败是**工具集膨胀**：功能重叠、边界模糊。判断标准很直接——**如果人类工程师都说不出该用哪个，模型更不可能。**
- 工具应自包含、对错误鲁棒、用途一目了然；参数要有描述性、无歧义。

## 例子：少而典型

- few-shot 仍是最佳实践之一；
- 但不要把边角案例堆成清单——**挑一组多样、典型、能代表期望行为的例子**；
- 对模型来说，例子是「一图胜千言」。

## 检索：从「预先塞满」到「即时取用」

| 做法 | 机制 | 代价 |
|---|---|---|
| 预检索（embedding） | 推理前先把相关资料捞进窗口 | 快，但可能过期、占预算 |
| **即时检索（just-in-time）** | 只保留轻量标识（文件路径、查询、链接），运行时用工具取 | 灵活、省预算，但慢，且依赖工具与启发式 |
| **混合** | 关键文件预先注入 + glob/grep 按需探索 | 多数生产系统的最优解 |

Claude Code 就是混合模式：`CLAUDE.md` 直接放进上下文，`glob`/`grep` 让它在需要时自己找文件，绕开了「索引过期」和「语法树复杂」两个坑。这也解释了为什么**目录结构、命名、时间戳本身就是上下文**——它们是给智能体的信号。

## 一条自检清单

- [ ] 系统提示是否能被压缩成「目标 + 约束 + 验收」，而不丢关键信息？
- [ ] 工具集里有没有两个功能重叠、模型会犹豫的？
- [ ] 例子是不是典型样本，而不是边角案例清单？
- [ ] 哪些信息可以改成运行时检索，而不是常驻窗口？
- [ ] 新增一段内容前，先问：它会不会挤掉更有价值的东西？
