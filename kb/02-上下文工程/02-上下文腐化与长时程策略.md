# 上下文腐化与长时程策略：压缩、笔记、子代理

> 结论：**长任务拼的不是窗口大小，而是「窗口满了之后怎么接得上」。** 三种做法各有适用面。

## 问题：窗口是硬上限

上下文会随对话、工具返回、文件内容不断膨胀，而注意力预算有限。到某个点必须做选择：丢、压、还是挪出去。

## 做法一：压缩（Compaction）

**做法**：临近上限时，把消息历史交给模型总结，用总结**重开一个窗口**。

Claude Code 的实现细节值得记：
- 保留**架构决策、未解决的缺陷、实现细节**；
- 丢弃**冗余的工具输出**与重复消息；
- 压缩后基于「摘要 + 最近访问的 5 个文件」继续工作。

**调优顺序**（原文建议）：
1. 先**最大化召回**——确保摘要能捕获轨迹里每一条相关信息；
2. 再**提升精确率**——删掉多余内容。

**风险**：压得太狠会丢掉「当时看不出重要、后来才关键」的上下文。

**最安全的轻量压缩**：清理工具结果。一个工具在历史深处被调用过，模型通常不需要再看原始返回。

## 做法二：结构化笔记（Structured note-taking / Agent memory）

**做法**：让智能体定期把笔记写到窗口之外（`NOTES.md`、待办列表、文件式记忆），之后按需拉回。

- 开销极小，却提供持久记忆；
- 适合**有明确里程碑**的迭代式开发；
- Claude 玩 Pokémon 的例子：跨数千步维持精确统计（「过去 1234 步我在 1 号道路训练，皮卡丘已升 8 级，目标 10 级」），上下文重置后读自己的笔记继续；
- 平台侧已有「基于文件的记忆工具」，支持跨会话维护项目状态、引用先前工作。

## 做法三：子代理架构（Sub-agent）

**做法**：主代理拿高层计划，把聚焦任务派给**干净上下文**的子代理；子代理可能烧掉数万 token 探索，只回传 **1,000–2,000 token** 的精炼结论。

- 关注点分离：搜索细节被隔离在子代理内部；
- 主代理只做综合与判断；
- 在复杂研究任务上明显优于单代理。

## 怎么选

| 任务特征 | 选 |
|---|---|
| 大量来回交互、需要对话流 | 压缩 |
| 迭代式开发、有清晰里程碑 | 结构化笔记 |
| 复杂研究/分析、并行探索收益大 | 子代理 |

三者不互斥：真实系统常常「笔记打底 + 子代理并行 + 临满时压缩」。

## 工程化要点

1. **压缩提示词要像代码一样测**：拿真实轨迹回归，看召回漏了什么。
2. **笔记要有固定结构**（目标 / 已完成 / 待办 / 为什么失败），否则模型写成一团。
3. **子代理的交付物要规定格式**：结论 + 证据 + 未解决项，避免回传一坨过程。
4. **别用压缩掩盖设计问题**：如果每轮都在压，说明任务该拆或该交给子代理。
