# 验证成为新瓶颈

> 来源 #60（宝玉xp）、#36。一句话：**想法不是瓶颈，验证才是。**

## 现场观察

「越来越多的发现是，Vibe Coding 到后来，**想法都不是瓶颈，验证才是**。很多想法不停地往上加，反正 AI 能帮你做出来，做出来了以后呢，根本来不及一个个功能测试。」

与手工编码时代的对比：

> 「以前写代码还需要反复测试一下，由于产出速度不高，是测得过来的，**有问题能马上知道在哪**。现在产出太快，功能已经多到测不过来。」

连 Codex、Claude Code 这样的产品也一样：用着用着就会遇到各种小 bug，本质是**用 AI 开发太快来不及测试**。所以「**做好测试覆盖各种场景，要做的工作量一点不少**」。

## 为什么会这样

**生成速度远超验证速度**，于是「代码产出量」与「可维护性 / 正确性」脱钩。传统开发中，写和测是同一个人的同一段时间；AI 把「写」压缩了 10 倍，但「测」没有同步压缩。

## 三种应对

| 手段 | 作用 | 注意 |
|---|---|---|
| **自动化测试 + 覆盖率** | 把验证也交给机器，让 Agent 能自验证 | 测试本身要可信，否则只是「假绿灯」 |
| **AI 评审** | 快速发现模式化问题 | 警惕「评审被同化」——评审者会接受被评审者的风格 |
| **可观测性**（日志、追踪、指标） | 让问题可定位 | 没有日志的 AI 代码，出错时只能靠猜 |

## 测试岗位会怎么变

不会消失，但会进化——**更需要懂业务、会设计场景、擅长用 AI 提效的人**；工作重心从「点点点找 bug」转向「**设计场景、制造真实验证**」。

这与「根基崩溃论」是同一枚硬币的两面：**AI 提升产出速度，同时侵蚀理解深度**；测试覆盖是应对手段之一。

## 一条可执行的纪律

```
每个功能合并前必须有：
1. 一个能复现需求的测试（失败 → 通过）
2. 一个边界用例（空值 / 并发 / 超时）
3. 一条日志，能在出问题时定位到「哪一步」
4. 一次人工抽查（不看代码，只看行为）
```

## 与「两头理论」的关系

验证之所以重要，是因为「越早纠偏成本越低」。AI 让编码变快后，**测试就成了那个「早」的位置**——它是唯一能在低成本阶段拦住错误的环节。
