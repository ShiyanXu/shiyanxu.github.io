# 思考强度（Effort）与 272K 上下文窗口

> 全批内容里最实用、也最容易踩坑的一条经验：**强度不是越高越好，它和上下文窗口耦合。** 来源 #59。

## 结论先行

- **GPT-5.6 Sol 推荐开 High 或更高**；
- **GPT-6 Astro 的 Medium 已经很强**——有些测试里 Medium 成绩反而更高，有些测试 Extra High 反而更费 Token。

原因主要与 Codex 的 **272K 上下文窗口**有关。

## 机制：超过 272K 会发生什么

当上下文长度**超过 272K** 时，Codex 会对上下文做**压缩（Compress）**。压缩的后果：

- 模型「记不清说过的话」；
- 「忘记用户下达的指令」；
- **连贯性工作被中断甚至产生偏移**。

因此交互式沟通时要**主动关注并触发 Compress**——在上下文快满之前主动整理，而不是等系统被动截断。

## 强度与任务形态的耦合

| 任务形态 | 高强度的问题 |
|---|---|
| 需要反复迭代、拆多步 | Extra High 可能过高，模型无法在一个 272K 窗口内完成「最小单位任务」，执行质量下降 |
| 偏向「写脚本迭代执行」 | Medium 比 Extra High 更倾向于多写几次脚本，**反而增加 Token 消耗** |

也就是说：**强度越高，单轮消耗的上下文越多，越容易提前触发压缩**——这是「思考强度不是越高越好」的根本原因。

## 实操建议（原文）

| 场景 | 建议 |
|---|---|
| 一边跟 Agent 聊天、一边让它做事 | **Very High**，并适时主动 Compress |
| 长期任务 | **Medium 更稳妥** |
| 想用 Very High 或更高 | 找一个**上下文更长的 Planner**（Kimi K3 / Fable 5.1）去指挥执行型 Agent |
| 不在乎 Token 消耗 | 直接把上下文改成 **1M** |

补充经验：**prompt 足够流畅的话，后台牺牲 effort budget 对最终质量应该没有影响。**

## 一张决策图

```
任务要跑很久、跨多轮？
├─ 是 → Medium + 主动 Compress + 固定目标文件
└─ 否 → 需要边聊边改？
        ├─ 是 → Very High（或 High）
        └─ 否 → Medium 起步，看结果再升
```

## 三个常见误区

1. **「拉满总没错」**：拉满会让单轮吃掉更多窗口，长任务反而更早失忆。
2. **「上下文越大越好」**：窗口大不等于召回准，超长上下文里中间部分容易被忽略。
3. **「压缩是系统的事」**：压缩会丢信息，什么时候压、压什么，应该由人决定。
