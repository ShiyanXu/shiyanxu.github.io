# 模型选型：能力、上下文、成本三维

> 编排形态见 [多模型分工与编排](../01-Agent心法/02-多模型分工与编排.md)；本篇只谈「选哪个模型、为什么」。

## 三个维度

| 维度 | 关键问题 | 表现 |
|---|---|---|
| **能力** | 会不会做 | 推理深度、代码正确率、指令遵循 |
| **上下文** | 一次能吃多少 | 窗口大小、压缩阈值、长文召回 |
| **成本** | 每次花多少 | 单价 × token 数（含思考 token） |

三者不可能同时最优，所以现实做法是**组合**：强模型做判断，长上下文模型做检索/核查，便宜的模型做批量执行。

## 一张实用对照

| 任务 | 选型倾向 |
|---|---|
| 定方案、拆任务、验收 | 最强推理模型，档位 High/Medium（忌 Max） |
| 读大量代码、跨文件核查 | 长上下文模型（1M 级） |
| 批量改写、跑测试、格式转换 | 中档 / 便宜模型，靠并行和重试取胜 |
| 探索式调试 | 上下文长 + 能边聊边改的模型 |
| 端侧/离线场景 | 本地小模型或决策模型（见 [端侧决策与沙箱基础设施](05-端侧决策与训练沙箱.md)） |

## 路由：把「选型」变成运行时策略

Claude Code Router（CCR）这类工具按「上下文 / 思考 / 后台 / 工具」等策略切换不同模型的 API，让长上下文模型（如 1M 窗口）与高性价比模型互补，最终效果「媲美顶级模型」。

最大收益不是省钱，而是**一次开十几个子 Agent 并发**时的成本与速度。

代价与难点：
- **tag 传递**：提示词里的标记必须如实传给被调用的小模型，否则任务会被派错；
- **一致性**：不同模型的输出风格不同，合并结果时要统一格式；
- **调试**：出问题时要知道是「哪个模型、哪一段」出的错。

## 档位（effort）不是越高越好

主模型用 High 就够（或 Medium），**切忌开到 Max 及以上**。原因是 Max 档单轮消耗上下文更多，更容易提前触发压缩，反而破坏长任务连贯性——机制详见 [思考强度与上下文压缩](02-思考强度与上下文压缩.md)。

## 什么时候值得用本地模型

| 值得 | 不值得 |
|---|---|
| 数据不能出内网 | 只是偶尔用一下 |
| 高频、低难度、批量任务 | 需要最强推理 |
| 需要离线/低延迟 | 显存不足以跑「满血上下文」 |

详细选型表见 [本地部署与量化](03-本地部署与量化.md)。
