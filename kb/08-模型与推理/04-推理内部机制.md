# 推理内部机制：一个 token 是怎么被算出来的

> 一次推理就是一次前向传播加一次采样：Prefill 吃算力，Decode 吃带宽，KV Cache 把省下的计算记成了显存和带宽的账。

## 全局图：从一段输入到一个 token

给模型「今天天气很好，我想去」，它要输出「公园」。中间是一条固定的流水线：

1. 文本切成 token；
2. 每个 token 变成向量；
3. 向量穿过 N 层 Transformer；
4. 最后一层输出每个位置的向量；
5. 取最后一个位置的向量，映射到词表大小；
6. 得到下一个 token 的概率分布；
7. 采样，选出这个 token；
8. 把新 token 拼回输入，回到第 3 步。

自回归生成不是一次写完一句话，而是一个 token 一个 token 往外蹦。每蹦一次，内部做的都是同一件事：**算下一个 token 的概率分布**。

一层内部的顺序固定：

```text
输入 → LayerNorm → Attention → 残差相加 → LayerNorm → FFN → 残差相加 → 输出
```

## 一层里只有两件事

| 模块 | 干什么 | 算什么 | 备注 |
|---|---|---|---|
| Attention | token 之间交换信息 | 当前 token 的 Q 与所有 token 的 K 匹配，softmax 后对 V 加权求和 | 多头并行做多组匹配，拼接后再线性变换 |
| FFN | 每个 token 自己消化信息 | W₂ · activation(W₁ · x) | 中间维通常是隐藏维的 4 倍，FFN 占一层参数的大头 |

Attention 回答的是「当前 token 该从哪些历史 token 那里拿多少信息」：Q 是「我在找什么」，K 是「我有什么标签」，V 是「我实际携带的信息」。MoE 模型把一个 FFN 拆成多个专家，每次只激活其中几个。

## 为什么只能一个一个出

训练时模型看得到整句话，每个位置的输出可以并行算。推理不行：第 t 个 token 依赖前面所有 token（P(x_t | x_<t)），生成完第 t 个，它才成为第 t+1 步的输入。

这条串行线消不掉，能做的只是把多个请求的串行线拼在一起跑。

## Prefill 与 Decode：同一个模型，两种计算形态

判断一个算子受谁限制，看算术强度：

```text
算术强度 = 浮点运算次数 / 访存字节数
```

强度高，计算多、搬数据少，容易 compute-bound；强度低，算得少、搬得多，容易 memory-bound。同一个模型，Prefill 和 Decode 恰好一头一个。

| | Prefill | Decode |
|---|---|---|
| 输入 | 整段 prompt 一次送进去，比如 1000 个 token | 当前这一个 token |
| 并行度 | 所有 token 并行算 Attention 和 FFN | 一次一个，串行 |
| 主要算子 | 大矩阵乘 | 矩阵向量乘 |
| 算术强度 | 高 | 低 |
| 通常的瓶颈 | 算力 | 内存带宽 |
| 优化看什么 | 算力利用率、矩阵乘效率、并行度 | 每步搬运的字节数 |

Prefill 里每搬一次权重，能参与大量计算，GPU 的计算单元容易跑满。Decode 每生成一个 token 都要重做一次完整前向，输入只有一个向量，却要读完全部模型权重和全部历史 KV Cache，算得少、搬得多。

## KV Cache：用显存换计算

Decode 时如果每来一个新 token 都把历史 token 的 K、V 重算一遍，计算量会爆炸。但历史 token 的 K、V 不会变，按层缓存下来即可。之后每步只算当前 token 的 Q、K、V，历史的 K、V 从显存直接读。

每个 token 的缓存大小固定，算式的 2 是 K 和 V 两组：

```text
每 token KV Cache 字节数 = 2 × 层数 × KV 头数 × 头维度 × 精度字节数
```

以 Llama-3-70B 为例：80 层、8 个 KV 头、头维度 128、FP16 每元素 2 字节。

```text
2 × 80 × 8 × 128 × 2 = 327,680 字节 ≈ 320 KB
```

8K 上下文，单个请求：320 KB × 8192 ≈ 2.56 GB。32 个并发就是 80 GB 左右，模型权重还没算进去，显存已经快满了。

线性增长的来源就在公式里：层数、KV 头数、头维度、精度都是模型的常数，只有序列长度在变。每多一个 token，就多一份固定的 320 KB；上下文翻倍，KV Cache 翻倍，每步要读的 K、V 也翻倍。

## 单 token 成本怎么估

Decode 单 token 的时间下界：

```text
单 token 时间 ≈ max(计算时间, 权重读取时间 + KV 读取时间)
权重读取时间 = 参数量 × 精度字节 / 带宽
KV 读取时间 = KV Cache 大小 / 带宽
计算时间 = 2 × 参数量 / 算力
```

算术强度低时，读取时间远大于计算时间，估的时候只留后两项：单 token 时间 ≈ 权重读取时间 + KV 读取时间。

代入 8B 参数、BF16、H100 的带宽与算力：

| 项 | 算式 | 结果 |
|---|---|---|
| 权重读取 | 16 GB / 3.35 TB/s | ≈ 4.8 ms |
| 计算 | 2 × 8e9 = 16 GFLOPs；16e9 / 503e12 | ≈ 0.032 ms |

计算 0.032 毫秒，等数据 4.8 毫秒，差 150 倍。计算单元大部分时间在空转，等权重和 KV Cache 从显存搬过来。

量化对 Decode 加速明显也是这个道理：它直接减少要搬运的字节数，而权重读取正是单 token 时间里的大头。

## 延迟与吞吐：两个不同的数

- 延迟：单个请求生成一个 token 要多久。
- 吞吐：整个系统每秒能生成多少 token。

增大批大小能分摊权重读取：同一份权重读一次，服务一批请求，吞吐随之上去。但每个请求的 KV Cache 还是要各读各的，批一大，单请求的等待可能变长。

所以推理系统都在解同一道题：在延迟和吞吐之间找位置。连续批处理、PagedAttention、PD 分离（Prefill 与 Decode 分开部署）、投机解码，都是在解这道题。

## 瓶颈判断：先看算术强度，再决定动哪里

| 症状 | 大概率瓶颈 | 先动什么 |
|---|---|---|
| Prefill 慢，GPU 利用率已经很高 | 算力 | 矩阵乘效率、算子实现、并行度 |
| Decode 慢，计算单元空转 | 显存带宽 | 减少搬运字节（量化）、加批摊薄权重读取 |
| 并发上不去，显存先满 | KV Cache 容量 | 缩上下文、降并发，压缩 KV 本身 |
| 单请求延迟够用、总吞吐不够 | 批没吃满 | 加批大小、连续批处理 |
| 上下文越长每步越慢 | KV 读取随长度线性涨 | 先缩上下文，再谈算子 |

归到一句：算子优化只对算力受限的环节有用；带宽受限时，减少搬运字节比优化计算更划算；KV 读取这一项由上下文长度直接决定，长度不降，别的优化都只是在分摊它。
