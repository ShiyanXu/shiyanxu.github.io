# AI 用量成本优化：把 token 花在刀刃上

> 结论：成本不是某一项设置，是三个因子相乘——**模型单价 × 每次带进上下文的体积 × 返工轮次**。原文的八条建议，每一条都能在里面找到位置。

## 先拆公式

| 因子 | 怎么变大 | 对应动作 |
|---|---|---|
| **单价** | 默认用最强模型、档位拉满 | 选型、推理档位、子代理降级、自动路由 |
| **体积** | 长会话、整套工具、没有项目地图 | 开新会话、压缩、按需开工具、吃住缓存 |
| **轮次** | 需求含糊、一步做到底、没有验证 | 写清提示与停止条件、分阶段、确定性护栏 |

三个因子里最容易被低估的是**轮次**：一次返工烧掉的 token，通常比一次选型失误更多。因为是相乘而不是相加，省轮次往往比省单价划算。

## 一、选型与档位：能力够用就好

| 模型档 | 适合的任务 |
|---|---|
| 推理模型 | 架构决策、复杂调试、系统设计、需要深分析的问题 |
| 中档 | 计划已经清楚，只差执行 |
| 轻档 | 重构、格式化、文档、范围明确的例行改动 |

两个反直觉点：

- **默认最强 ≠ 结果更好**。token 上去了，质量没上去；在执行型任务里，推理模型会「想太多」，反而引入无关改动。
- **能力按任务给**。用多少能力取决于任务需要多少，不是取决于你怕不怕出错。

**推理档位**同理：档位越高，单轮吃的 token 越多，默认用常规档，只在难题上抬高。档位为什么还会反过来伤长任务，机制见 [思考强度与上下文压缩](02-思考强度与上下文压缩.md)。

## 二、自动路由：把选型交给系统

Copilot Fusion 是运行时的**模型路由 + 编排器**，在模型选择器里选中它，选中的不是某个模型。它按每个请求从三种执行模式里挑一种：

| 模式 | 做法 |
|---|---|
| 单模型 | 一个模型做完 |
| 级联 cascade | 便宜模型先起草，评审模型决定「接受」还是「升级给更强的模型」 |
| 评审 critique | 一个模型起草，多个模型并行批评，汇总后起草模型再改 |

配套三档 effort：**Standard**（平衡成本、质量、延迟）、**High**（编排更重、中等省 token）、**Max**（前沿能力，但仍考虑 token 效率）。计费上按所用模型的标价分别结算，Fusion 本身不另收费；但 High / Max 可能一次任务动用多个模型，因此比 Standard 更费 AI Credits。

Fusion 有一个和成本直接相关的设计：**尽量把主会话留在同一个模型上**吃缓存，辅助模型（如 reviewer）只拿它需要的上下文。

## 三、子代理用便宜模型

子代理跑在自己的会话里，不继承主会话的对话历史，上下文只服务一个聚焦任务——所以轻模型通常够用。而且给它降级**不会**像「会话中途换模型」那样打掉主会话的缓存，见下一节。

## 四、缓存：最容易被顺手打掉的钱

缓存让模型不必每轮重算同一段上下文。在 Agent 编码里，系统提示词、文件内容、工具定义这些大头会被反复发送，所以缓存的收益很大：**缓存命中的部分，通常按正常输入价的 10% 计费**。

反过来，下面三件事会把缓存打掉，导致整段上下文按新输入重新计费：

| 动作 | 原因 |
|---|---|
| 会话中途换模型 | 不同模型不能复用彼此的缓存 |
| 回到闲置很久的旧会话 | 缓存会过期：OpenAI 模型约 24 小时，其他模型约 1 小时 |
| 会话中途改推理档位、上下文大小、启用的工具或 MCP | 这些设置变化会让缓存失效 |

对策只有一句：**开会话前把模型、档位、工具配好，整个会话不动**。要接着旧会话跑，先压缩，让重建的是短摘要而不是全部历史。

## 五、上下文卫生

- **换问题就开新会话**。CLI 里 `/new`（或 `/clear`），Chat 里新开一个会话。旧线程会把全部历史带进每个新请求。
- **长会话要续命就压缩**。CLI 里 `/compact` 把历史总结成摘要，还能聚焦：`/compact focus on the auth module`；`/context` 随时看当前用量。
- **给一份项目地图**。`AGENTS.md` 或 `copilot-instructions.md` 让 Agent 不必读几十个文件来定位，写法见 [AGENTS.md：给 Agent 的项目上下文文件](../13-工程实践/02-AGENTS-md与项目上下文.md)。
- **工具按需开**。一整套 MCP server 的工具定义每次请求都进上下文，只开这个任务用得上的。

## 六、提示写清楚，省的是整轮返工

好提示有三个特征：

1. **任务定义清楚**。别写「修一下这个 issue」，要说清是什么问题、在哪、期望结果是什么样。
2. **相关上下文提前给**。已经知道哪些文件、服务、日志、报错相关，直接给，别让 Agent 自己探索。
3. **停止条件明确**。说清「做完」长什么样。没有停止点，Agent 会靠追加提交、顺手重构无关代码、扩大范围来「继续努力」。

这些文字本身几乎不增加 token，减少的是达成正确结果所需的运行次数。分层写法见 [提示词的分层与工程化](../03-提示词工程/05-提示词的分层与工程化.md)。

## 七、分三段做：研究 → 计划 → 实现

把三件事挤在一个会话里，上下文会迅速膨胀，无关信息跟着堆积。

| 阶段 | 做什么 | 用什么 |
|---|---|---|
| 研究 | 探索代码库、找相关文件、理清依赖 | 能读能搜的 Agent |
| 计划 | 先写结构化计划或规格 | **强推理模型**（CLI `/plan`；VS Code Chat 选 Plan）|
| 实现 | 照计划执行，上下文只留这一段需要的 | 便宜的执行型模型 |

关键动作是**阶段之间开新会话**，每段只带自己需要的信息；计划做完再用便宜模型执行，是这套流程里最直接的省钱点。

## 八、把洞察沉淀成常驻指令

- CLI 里 `/chronicle tips` 分析近期会话，找出提效机会；`/chronicle cost-tips` 看 token 消耗模式、找降本点。
- 当反复出现同一种模式——某个工具被过度调用、某个提示总被误读——就把它写进 `copilot-instructions.md`。

这条的杠杆在于位置：指令文件每次运行都在上下文里，改一次，之后每个会话都受益，不用靠人记着重复。

指令要短、要具体、要基于真实观察到的行为，而不是听起来正确的通用最佳实践。写什么、不写什么的清单见 [AGENTS.md：给 Agent 的项目上下文文件](../13-工程实践/02-AGENTS-md与项目上下文.md)。

## 九、加确定性护栏

Agent 不是确定性的，多步流程里小错会复利：在错误的输出上继续建，越偏越远，debug 越来越贵。

三类能给出明确 pass / fail 的控制：

- **单元测试**：验证改动产生了预期行为；
- **Linter**：管住结构与风格漂移，省掉清理工作；
- **安全扫描**：在问题还容易回滚时抓到。

三者合起来是个紧反馈环：改 → 验 → 调，Agent 在继续之前就修正。前期每步可能多花一点 token，换掉的是整条错误链——投入护栏的团队通常总消耗反而更低。「做完了」怎么判定见 [完成判定与端到端验证](../15-Harness精读/笔记/06-完成判定与端到端验证.md)。

## 十、给单次会话设上限

CLI 与 SDK 支持在开工前设一个 AI Credits 会话上限：到点 Agent 干净停止、通知你，由你决定继续还是提高上限。

两个用法：

- 防意外超支；
- 调效率时，找「还能出好结果的最低配额」。

注意它是**软限制**，管单次任务，不替代用户级的月度预算与支出上限。

## 自查表

| 症状 | 先查 |
|---|---|
| 账单突然涨 | 是不是中途换了模型、改了档位、或回到闲置的旧会话（缓存被打掉） |
| 一个任务跑很多轮 | 提示里的任务定义与停止条件 |
| 长会话越跑越糊涂 | 该开新会话或 `/compact` 了 |
| 每轮都慢且贵 | 工具集太大、项目没有地图、档位开太高 |
| 返工多 | 先补单测 / lint / 安全扫描 |
