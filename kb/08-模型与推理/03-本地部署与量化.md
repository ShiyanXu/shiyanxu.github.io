# 本地部署与量化选型

> 按显存对号入座，同时理解「为什么上下文这么吃显存」。来源 #41。

## 显存档位对照表（Qwen3.8 系列为例）

| 显存 | 模型 / 量化 | 体验评价 |
|---|---|---|
| 12G 及以下 | Qwen3.8 9B（蒸馏版） | 可试，但大概率「比豆包流还长」，不如直接买 token |
| 16G | 27B Q3_K_M | 体验约等于本地养一只豆包 |
| 24G | 27B Q4_K_M | 上下文非常吃紧，或选「一只满血上下文的本地豆包」 |
| 32G | 27B NVFP4 + 满血上下文 | **推荐** |
| 48G | 27B FP8 | 比较尴尬：FP4/Q4 没提升，又没有更合适更大的模型 |
| 72G | Flash 180B NVFP4-Fast | 分块量化、实际需约 68G，上下文基本不占地方 |
| 96G | Flash 180B（ROCm / FP4-FAST） | 普通人的 96G 基本是 Strix Halo；效果超预期，能跟 DSV4Pro「有来有回」 |
| 96G（另一档） | Flash 180B NVFP4-STRIX | 占用约 87.9G，同条件下速度慢不少，需要狂暴算力 |
| 128G | — | 作者「没有发言权」，进入更高级别 AIPC 就随便挑 |

## 量化格式扫盲

| 名词 | 含义 |
|---|---|
| **Q4_K_M / Q3_K_M** | llama.cpp 的 K-quant 系列。`Q` 为量化、`K` 为 k-quant 算法、后缀表示每块位数与混合策略；数字越小越省显存、精度损失越大；`M` 为 medium 混合档 |
| **FP8** | Hopper 世代起广泛支持的高效格式 |
| **FP4 / NVFP4** | NVIDIA Blackwell 世代的低精度格式。**NVFP4** 是专为 Blackwell 优化的 4-bit 浮点（含 block scaling），同显存下通常比传统 INT4 精度更好 |
| **ROCm** | AMD 的 GPU 计算栈（对标 CUDA），Strix Halo 等平台走这条路线 |
| **满血上下文** | 能承载模型宣称的最大上下文长度（如 128K/256K）所需的 KV Cache 显存 |

## 为什么「上下文吃紧」：KV Cache 原理

Transformer 推理时，已生成 token 的 Key/Value 张量会被缓存以避免重复计算。

```
KV Cache 大小 ≈ 2 × 层数 × 头数 × head_dim × 序列长度 × 精度字节数
```

关键结论：**随上下文长度线性增长，与参数量无关**。

这解释了两个看似矛盾的现象：

- 24G 跑 27B Q4_K_M，参数勉强装下，但**上下文非常吃紧**；
- 72G 跑 180B NVFP4，参数大得多，**上下文却基本不占地方**（因为用了分块量化 + 更长的上下文预算分配）。

## 快速决策

```
显存 >= 96G（统一内存 / 多卡） → 180B 级 NVFP4，追求「能打」
显存 32~72G                     → 27B~72B 的 FP8/NVFP4，或 180B 分块量化
显存 16~24G                     → 27B Q3/Q4_K_M，接受上下文受限
显存 <= 12G                     → 建议直接用云端 API，本地意义不大
```

## 本地 vs 云端的判断

| 选本地 | 选云端 |
|---|---|
| 数据不能出内网 | 偶尔用、用量不稳定 |
| 高频调用，长期算下来更省 | 需要最强推理能力 |
| 需要离线/低延迟 | 没有显卡或显存不足 |
| 想自由改模型/微调 | 不想维护环境 |
